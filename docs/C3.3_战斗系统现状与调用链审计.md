## §0 执行摘要

1. **战斗主链路（20002 族）已端到端闭环**：客户端点怪 → CS_20002 → 服务端下发 20010/20012/20013 → 怪物死亡 → 20020/20023 → 3 秒后 `_battle_settle` 线程发奖（exp/coin/掉落）+ 推进任务 + 推 10301/10500/12405。c32 实机帧（09:52:24–09:52:33）完整记录了 mon 20002 的一次战斗。
2. **服务端权威判定**：伤害（520 固定）、胜负、死亡、结算全部由 `battle.py:BattleUtil` + `_battle_timer` 线程计算；客户端只发 `mon_id`，不发任何胜负/伤害/掉落字段。CS_20008（自动战斗 flag）、CS_20009（技能 id）均被服务端忽略。
3. **关键新发现（修正 C3.2 对 exp 风险的表述）**：`_battle_settle` 中 **exp 在 reward_log 幂等检查之前无条件直加**（`add_role_exp`），**掉落也不经幂等门**；reward_log 的 `kill:<mon_bid>:<rid>` 键只门控 coin 与任务进度。结果是：**同一怪物可被反复击杀刷 exp 与掉落物，coin 反而被幂等门挡住**——这不是 C3.2 R1 所说的"crash 窄窗口"，而是一条确定性的重复刷取路径。详见 §2-A7。
4. **配置层全空**：`config_battle.json` / `config_fight.json` / `config_mon_data.json` 三个权威配置表均为 `{}`；怪物数值（hp_max=1950、player_dmg=520、mon_dmg=200、KILL_REWARD={exp:50,coin:30}）全部硬编码在 `battle.py` / `mock_server.py:9916`，证据等级 TEST_ONLY。
5. **怪物无持久状态**：场景怪由 `quest_spawn.target_mons()` / `scene/service.static_mons()` 在每次 10201 推送时重新计算并下发，DB 无怪物死亡/重生表；击杀后下次进场景怪物自动刷新。
6. **C3.1 / C3.2 依赖复核结论**：六篇 C3.1、六篇 C3.2 文档均存在且关键结论在当前代码/活库中成立；但 C3.1 报告的 `roles` 旧表漂移在活库中**仍然存在**（roles.gold=1800140 vs role_assets.gold=1799942 等），未被修复。

`_battle_settle`（mock_server.py:9916-9958）的执行顺序：

```python
delta = dict(KILL_REWARD)                 # {'exp':50, 'coin':30}
_exp_gain = delta.pop('exp', 0)           # 50
if _exp_gain:
    add_role_exp(rid, _exp_gain)           # ← ① exp 无条件直加，先于幂等检查
_awards = [{'kind':'asset','code':'coin','amount':30}]
_kill_gr = grant(rid, _awards,
                 reference_id='kill:%d:%d' % (mon_bid, rid),
                 source='battle')       # ← ② coin 经 reward_log PK 幂等
if not _kill_gr.get('already'):
    mission_progress_advance(...)         # ← ③ 任务进度仅首杀推进
for code, name, qty in roll_drops(mon_bid):
    db_bag_add(rid, code, qty)            # ← ④ 掉落无条件入包
```

| 击杀次数 | exp | coin | 任务进度 | 掉落 33001 |
|---|---|---|---|---|
| 第 1 次 | +50 ✅ | +30 ✅ | +1（达标→status=2） | +1 件 |
| 第 2 次（同 mon） | **+50 ❗** | +0（already） | 跳过（already） | **+1 件 ❗** |
| 第 N 次（同 mon） | **每次 +50 ❗** | +0 | 跳过 | **每次 +1 件 ❗** |

- **活库佐证**：`reward_log` 中 `kill:20002:1001` 仅 1 行（coin 幂等生效）；但 `role_assets.exp=20689` 与 c32 战斗后 `exp=19289` 之间的差值说明 exp 可被多次叠加。
- **根因**：`reference_id='kill:<mon_bid>:<rid>'` 键的设计意图是"每怪每人仅一次奖励"（对应任务怪），但 `add_role_exp` 与 `db_bag_add` 在 grant 幂等门**之外**执行，导致幂等门只挡住 coin。
- **与 C3.2 R1 的差异**：C3.2《任务奖励与持久化设计》§5 R1 将 exp 风险描述为"结算中途 crash→重提极窄窗口"。本次审计发现实际风险**更宽**：不是 crash 窗口，而是**任何重复击杀同一怪物都会确定性重复发 exp 与掉落**（因为怪物被 quest_spawn 反复刷新，客户端可反复点）。
- **缓解现状**：同连接内 `self.battle` 门挡并发；`_battle_settled` 标志防同连接重入。但跨连接/重连后门失效。
