## §1 奖励结算路径（12403 → 发奖 → 落库）

### 1.1 调用顺序（C 分片 §2 复核结论，引用）

12403（CS_12403{mission_bid}）在服务端旧链 handler（`mock_server.py:16632-16783+`，C 分片后行号见各门禁）结算时，奖励按以下顺序落账：

```
CS_12403 bid=X
  ├─ [幂等1] status==3 短路 → 直接 code=1，不发奖（mock_server.py:16699-16677 区间，D 项11实证）
  ├─ [门禁]  status != 2 → code=0 "condition not met"，不进入结算（C 分片 I3，:16705 起；D 项5实证）
  ├─ 解码 award_assets（decode_award_assets，mock_server.py:4567+）→ delta 字典
  ├─ _exp_gain = delta.pop('exp')        ← exp 单独抽出
  │     └─ add_role_exp(rid, _exp_gain)   ← exp 直加（见 §4.1 窄窗口风险）
  ├─ grant(rid, _awards, reference_id='task:<bid>:<rid>', source='task')
  │     └─ reward/service.py:51-58 先查 reward_log PK 后入账（见 §2）
  └─ db_save_mission(status=3, commit_num+1)   ← 最后落库状态
```

> 引用：C 分片 §2「发奖顺序：add_role_exp → grant(资产,reward_log 标记) → 落库 status=3」。

### 1.2 无"已结算但奖励丢失"窗口论证（C 分片核验结论引用）

- **先领奖、后落库状态**：奖励（exp 直加 + grant 资产）发生在 `db_save_mission(status=3)` **之前**。这意味着不存在"状态已置 3 但奖励尚未发放"的窗口——若落库前进程崩溃，DB 里 status 仍为 2（或 1），重提会重新走完整结算；而奖励是否重发由 §2 的 reward_log PK 兜底。
- **先标记、后落库的反向风险已被规避**：grant 内部先写 reward_log（reference_id 命中即 already），再改资产；即使 grant 与 db_save_mission 之间崩溃，重提时 reward_log 已有 `task:<bid>:<rid>` 一行 → grant 返回 already、资产不变 → 再落库 status=3，不会二次发奖。
- **实机证据**：
  - D 项 7：提交后 reward_log 恰好新增 1 行 `reference_id="task:10020:2001" source="task"`。
  - D 项 11：重复提交 status==3 任务，code=1 且 `asset_delta={coin:0,hero_exp:0,exp:0}`、`exp_delta=0`（资产零变化）。
  - C 分片 §3.3：幂等重提 10070 → code=1，资产零变化（delta2 全 0）；reward_log `task:10052..task:10070` 各仅一条。
- **结论（证据 A）**：奖励结算路径不存在"已结算但奖励丢失"窗口；常规重提/断线重连/进程重启均不重复发奖。

| 项 | 证据 |
|---|---|

## §3 任务状态与奖励一致性设计

### 3.1 status 枚举（A 分片 §2.2 实证，修正 C3.1 漏值）

| status | 语义 | 是否落库 | 落点 | 证据 |
|---|---|---|---|---|
| 0 | 可接取未接 | 不落库 | `mock_server.py:5132 accept_mission_rows()` 内存构造，喂 SC_12407/12409 | A（代码） |
| 1 | 已接取进行中（条件未满足，且非链头） | 落库 | `task/service.py:96` 播种、`:141` 降级 | A |
| 2 | 条件已满足/链头，可提交 | 落库 | `:129-139` 提升、`:96` 无条件任务播种即 2 | A |
| 3 | 已完成已结算 | 落库；12421 完成列表只收 status==3 | `mock_server.py:19427-19429` | A（活库 5 行实证） |

> ⚠ C3.1《统一数据模型》原枚举漏 status=2，按 A 分片 §2.2 修正为 0/1/2/3 四值。

### 3.2 结算时机与一致性

- **只有 status==2 才能进入结算**（C 分片 I3 门禁，`mock_server.py:16705` 起）。D 项 5 实证：击杀前提交 10020（status=1, value=0/1）被拒 `code=0 "condition not met 0/1"`。
- **结算成功 → status=3 + commit_num+1**，奖励随 12403 同批发出（资产刷新走 10301/10302/10303）。
- **status==3 后任何重复提交短路 code=1、不二次发奖**（双层幂等：status 短路 + reward_log PK）。
- **状态归一（T7）**：`task/service.py:120-146` 每次 mission_rows 时把"条件已达标但 status 仍 1"提升为 2，把"status=2 但实际未达标"降回 1，保证 DB 状态与 value/target_value 始终一致。

## §4 持久化设计

### 4.1 missions 表结构（活库实证 13 列）

`persistence/db.py:89-95` 建表（唯一权威；`mock_server.py:4709-4715` 为注释掉的旧建表）：

```
missions(
  rid, mission_bid, mission_status, process_status,
  target, target_value, value,
  commit_num, loop_count, loop_num, code,
  accept_time, updated_at,
  PRIMARY KEY(rid, mission_bid)
)
```

共 13 列 + 复合主键 (rid, mission_bid)。证据 **A**（A 分片 §2.5）。

### 4.2 读写入口

| 入口 | 位置 | 说明 |
|---|---|---|
| 读 | `task/service.py:158-168` `db_get_missions` | 按 rid 读全部任务行 |
| 写 | `task/service.py:171-188` `db_save_mission` | `INSERT OR IGNORE` + `UPDATE` upsert |

### 4.3 重登 / 重启恢复（D 分片 E2E 实证）

| 场景 | 测试 | 结果 |
|---|---|---|
| 断线重连后 missions 一致 | D 项 9：close socket → reconnect → 1110 → 10102 → 10300 | **PASS**：10010=3/10020=3/10030=2，coin/exp/hero_exp 均不变 |
