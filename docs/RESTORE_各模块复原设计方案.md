## 一、先定义"复原"是什么

本项目的"复原"**不是**重做游戏，而是：

> **让原版 1.4.9 客户端的每个面板/玩法，在自建服务端上呈现出与原版一致的行为与数据。**

三条判据（缺一不可）：

| # | 判据 | 反例（本项目踩过） |
|---|---|---|
| 1 | **面板不空、不卡** | `10924` 活动列表曾回空表 ⇒ 活动面板无内容 |
| 2 | **数据是"真话"** | `12832` 曾"回成功但不扣费不发货" ⇒ 玩家以为买到了 |
| 3 | **行为可复算** | `10304` 的 `attr` 曾按平铺 u32 写 ⇒ 客户端字段整体错位 |

**已确立的纪律**（继续沿用）：
原版 APK 是最终标准 ｜ 不猜编码（规格来源：`AutoConstruct spec` > reader 原型 > 抓包长度）
｜ 无依据的数值标"占位" ｜ 每模块必须有**逐字节验证脚本**与**可回滚点** ｜ 每轮出 `roundN` 报告

## 四、★ 四个横切主题（决定所有模块的形态）

### 横切 1：属性/战力闭环（P0，卡着"变强面板"）

**问题**：面板读 `RoleVo.power[1].val`，`10304`（属性+power）与 `20100`（战力分量）都已实现，
但运行时探针证明 **`RoleVo.power` 从未被任何消息写入** ⇒ 存在一条**未定位的"角色属性同步消息"**。

**三条候选路线**（§7 问题 2 会问）：
- **A 全量重构**：按 `_attr_data.json` 的 `AttrLen=64` 重建属性表 —— 只存**输入项**、
  变更后**派生重算**、按 `AttrKeyIsShow` 配置决定**可见性白名单**。彻底但要动 DB 与多处读点。
- **B 定向追因**：只在**取证的范围内**继续找那条同步消息（沿用现有 25 列，不动模型）。
  风险最低，但可能长期找不到。
- **C 折中**：先补 `role_attr` 的**输入/派生标记**（不改列数），让 `10304` 能算出与原版一致的 power，
  同时并行查找同步消息。

### 横切 2：账号/会话层

**现状**：`1110` 的角色列表来自 `config.json`，**不查 `roles` 表**；无 password/token/account 表。
**影响**：单机单人可跑；但**多角色测试**、重登、账号隔离都做不了。
**候选**：不动（保持单机单人） / 加最小 account 表（多角色） / 完整会话层（token+过期）。

### 横切 3：工程拆分（`mock_server.py` **7265 行**）

if 链已达维护上限。round42 抽 `shop_try_buy()` 是正确方向（三处购买入口共用一处实现）。
**候选**：立刻按域拆 `handlers/*.py` / 边做新模块边拆 / 不拆。

### 横切 4：★ 与真机玩家共存（本轮新增的现实约束）

调试期间发现**真机客户端正在活跃游戏**（模拟器登录/移动/购买/心跳）。
⇒ 已确立两条纪律：**不要再"还原 DB"**（会毁玩家进度）、**有玩家时别跑 `replay_captures.py`**
（876 变体会真实扣费/发货）。

**候选变更窗口**：随时可重启（客户端会自动重连） / 约定时段 / 只做热更（不重启）。

## 五、逐模块复原方案（未实现模块）

> 每个模块统一模板：**数据源 → 协议范围 → 表设计 → 实施步骤 → 验证 → 风险**

### 模块 13：副本 / 爬塔（`130` / `213` / `196`）

- **数据源**：`config_dungeon_new`（普通副本）、`config_dungeon_tower`/`config_single_tower`/`config_golden_tower`
  （塔类）、`config_dungeon_reward_desc`（奖励描述）、`config_dungeon_endless_data`（无尽）
- **真机在发**：`13005`（副本信息）、`13034/13036`（魔塔）、`13045`（爬塔层数）、`13052`（试炼难度）、
  `13058`（副本分数）、`21301`（塔记录）—— 现均回零值
- **表设计（新增）**：
  ```
  dungeon_progress(rid, dung_bid, clear_cnt, best_score, last_clear_ts, day_cnt, week_cnt)
  tower_progress (rid, tower_id, floor, best_floor, clear_list_json)
  ```
- **步骤**：① 提取副本配置 → ② 建表 → ③ 实现"查询类"（回**真实进度**，替代零值）
  → ④ 实现"进入/结算"（复用 `battle.py` 的回合编排）→ ⑤ 奖励发放走既有 `db_bag_add`
- **验证**：`verify_dungeon.py`（逐字节规格 + 打通一次副本后进度落库）
- **风险**：副本战斗与原版编排可能不同 ⇒ 首版只保证"能进能出能结算"，数值标注【占位】

### 模块 14：宗门（`135` / `175`）

- **数据源**：`config_guild`（宗门等级/权限）、`config_guild_mission`（宗门任务）、
  `config_guild_skill_data`、`config_guild_tree_data`、`config_guild_pray`、`config_guild_animal`
- **真机在发**：`13500/13501`（宗门信息/成员）、`17501`（宗门战）
- **表设计**：`guild(id, name, lev, exp, fund, owner_rid, create_ts)` + `guild_member(rid, guild_id, pos, contrib)`
- **步骤**：① 最小可玩：**建宗/入宗/宗门任务** 三件套 → ② 宗门战（`17501`）单独一轮
- **风险**：宗门战涉及跨服与匹配，**单机环境下无对手** ⇒ 建议只做"宗门日常"，战事回"未开放"

### 模块 15：竞技场（`113`）

- **数据源**：`config_arena_data`（对手编队）、`config_trophy_arena_data`（段位）、`config_arena_msg`
- **真机在发**：`11300/11308`（信息/战绩）
- **表设计**：`arena_record(rid, day_cnt, win, lose, score, rank, last_ts)`
- **步骤**：① 查询类回真实战绩 → ② 挑战走 `battle.py` 对**配置生成的 NPC 编队**
  → ③ 段位/积分结算（`10302` 推送刷新）
- **风险**：真机排行榜需要多角色 ⇒ 单机只能"自己 vs 配置对手"

### 模块 16：组队（`132`）

- **数据源**：`config_team_destination`（目标副本）
- **真机在发**：`13200`（队伍信息）、`13201/13224/13227`（成员/人数）
- **判断**：单机单角色下**组队无意义** ⇒ 建议**只做"单人队伍"**（自己当队长、人数 1），
  让依赖队伍人数的活动（如 `17001` 的"至少 3 人"）回**真实人数 1** 而不是零值
- **风险**：低。可作为"让若干依赖队伍的判断变真"的低成本铺垫

### 模块 17：社交 / 聊天（`127` / `133` / `205`）

- **数据源**：`config_chat_bubble`（气泡）、`config_friend_zone_data`、`config_friend_regress`
- **真机在发**：`12762`（聊天）、`13341/13342/13343/13359`（社交圈）、`20504`（好友任务）
- **判断**：单机环境下**没有真人好友** ⇒ 社交类的"空"其实是真话。
  有价值的部分是：**聊天频道（世界/系统公告）**—— 服务端可以真的发系统消息，让聊天面板有内容
- **候选**：只做系统公告/聊天回显（面板有内容） / 不做

### 模块 18：婚宴 / 庭院 / 庄园（`183` / `155` / `158`）

- **数据源**：`config_garden_data`、`config_manor`、`config_marry_data`/`marry_eqm_data`
- **判断**：婚姻系统需要两个角色 ⇒ **单机下不可复原**（除非允许"与 NPC 结婚"的自造规则）
- **候选**：跳过 / 只做"庭院种植"这类**单人可玩**的部分（`15501/15801` 现在回空）

### 模块 19：养成线（翅膀 / 法宝 / 命格 / 符文 / 称号 / 坐骑 / 魂星）

- **数据源**：全部齐备（`config_wing_data`、`config_fabao`、`config_mingge`、`config_rune_data`、
  `config_title`、`config_ride`、`config_rune_treasure_data`…）
- **判断**：这是**与战力直接挂钩**的一组，且**都是"服务端供给列表"**（正是本项目最擅长的一类）
- **建议**：按"玩家最容易点开"的顺序做：**翅膀 → 法宝 → 坐骑 → 命格 → 符文 → 称号**
- **注意**：round40 已确立 `attr` 是**表**（`u16计数 + 4×u16 + 20×u32`）⇒ 这些模块的属性下发
  必须按该结构写，`power_*` 分量要**与 `10304` 同源**（统一走 `role_power()`），否则又会出现"两处战力不一致"
- **风险**：**中等偏低**，且能直接改善"变强面板"

### 模块 11（收尾）：排行榜剩余 3 榜（`12902` / `12911` / `12912`）

- **卡点**：榜名是资源 id（`config_rank` 只给 `type/title`），而资源清单 `all_res_file.luac`
  **不是 LuaJIT dump** ⇒ 指标（`val` 含义）未取证
- **解锁路径**：① 从 Android 资源表（`resources.arsc`）反查 txt 资源名；
  ② 或找另一份未加密清单；③ 或观察真机**已购/已领**行为反推
- **解锁后**：照 `12901` 的模式补真实 `val`，成本很低

## 八、★ 已确认决策（2026-09-19 项目方拍板）

| # | 决策点 | **选定** | 落地含义 |
|---|---|---|---|
| 1 | 路线 | **B —— 补齐「可玩系统」** | 顺序：副本爬塔 → 竞技场 → 单人队伍 → 宗门日常 |
| 2 | 属性/战力 | **A 折中** | 先补**输入/派生标记** + 让 `10304`/养成线/排行榜**统一走 `role_power()`**；**并行**继续找那条同步消息 |
| 3 | 账号/会话 | **B 最小 account 表** | 支持**多角色**（便于测试不同职业/等级、并验证 AOI 与排行榜真实数据） |
| 4 | 复原度纪律 | **A 严格不猜** | 未取证一律回**零值/未开放**；绝不出现"假成功" |
| 5 | 工程拆分 | **A 边做边拆** | 新模块**直接写成 `handlers/*.py`**，旧 if 分支逐步外移；`mock_server.py` 只做装配与分发 |
| 6 | 变更窗口 | **A 随时可重启** | 客户端会自动重连；重启前**必须先跑三道无副作用审计**确认基线 |

**由决策推出的两条硬约束**：
- 因 **#4 严格不猜**：每个模块的"结算/掉落/数值"若原版取证不到 ⇒ 只能标【占位】或回零，
  **不能为了"能玩"而编数值**。这会拉长单模块周期 ⇒ 必须优先做**取证充分**的模块。
- 因 **#1 路线 B**：副本/竞技场都需要**对手编队**与**战斗编排**，而 #4 不允许编数值
  ⇒ 首版走**"进度快照真实 + 战斗沿用既有 `battle.py` 编排"**，把"数值是否与原版一致"单列待校准项。

## 九、★ 实施轮次计划（按已确认决策排定）

> 每轮统一交付：`handlers/<域>.py` 新模块 + `verify_<域>.py` 逐字节校验 + `analysis/1.4.9/roundN_<域>.md` 报告
> 每轮收尾必跑：`audit_sc_conformance.py --generic --unsupported`、`audit_sc_live.py --unsupported`、
> `audit_specs_vs_fields.py`（**有真机玩家在玩时不跑 `replay_captures.py`**）

| 轮次 | 主题 | 交付物 | 验收标准 |
|---|---|---|---|
| **R43** | **属性/战力折中（P0 横切）** | `role_attr` 补 `src`(input/derived) 标记；`role_power()` 成为**唯一战力口径**（`10304`/`12901`/养成线全走它）；`_attr_data.json` 的 `AttrLen=64` 与现有 25 列的**差异清单**落文档 | 三处战力数值**完全一致**；差异清单明确"哪些属性属派生、哪些缺失" |
