### 3.1 注册与分发
1. **命令入口**：新增 CS 命令必须在 `mock_server.py` 的 if-cmd 链（`if cmd==N` / `elif cmd==N` / `cmd in(...)`）注册真实 handler；当前 DISPATCH_TABLE（`server/core/dispatch.py`，mock_server.py:38-44）为空兼容层，**新 handler 落地时必须同时留 DISPATCH_TABLE 兼容入口**（`@register` 或表项），便于后续从旧 if 链平滑下沉，禁止只写 if 链不留入口。
2. **模块归属**：业务逻辑放 `server/<mod>/service.py` + `<mod>/handler.py`；mock_server 顶部 `import <mod>.handler` 触发 `@register`（参照 :101 growth.handler / :102 answer.handler / :104 scratch.handler / :105 friend.handler / :103 growth_target.handler 既有模式）。新模块**禁止 import mock_server**（循环 import 红线，HANDOFF §五）。
3. **改前备份**：动 mock_server.py 前存 `.bak_rXXX`（现有 r72~r242 备份链），失败即回滚。

### 3.2 标准处理顺序（每个 CS handler 必须遵守）
```
① 帧解析：protocol/frame 解包 → 取 cmd/rid/payload
② 请求校验：rid 会话归属、字段范围（uint16/uint32 边界）、前置条件（等级/任务/背包格）
③ Service 业务：走 CurrencyService / RewardService / ItemService / AttributeService / PowerService / 对应玩法 Service
   —— 资产变动只走 currency.service db_add/db_set_assets；
   —— 发奖只走 reward.service.grant（带 transaction_id，幂等）；
   —— 属性/战力变动走 attribute.service + power.service 重算。
④ 持久化：persistence/db.py db_conn/db_release 写库（roles/role_attr/role_assets/业务表）
⑤ SC 推送：SessionRegistry.push_to_rid → SC 回包 + 关联增量推送（SC_10301 属性 / SC_10303 资产 / SC_10502 背包 / SC_10304 战力）
```
**禁止**：绕过 Service 直接 SQL 改 role_assets / role_attr / bag_items（HANDOFF 硬纪律 #4）；GM 修改也必须走正式 Service 链路（P13 已落地）。

### 3.3 错误处理 / 回滚 / 幂等
- **错误码**：业务失败回 SC 错误位（沿用现有协议帧内错误字段），不擅自新增码段；未定义错误码先在本文件登记，禁止凭空造码。
- **回滚**：③④ 间任何 Service 异常 → 不写库、不推送增量，回 SC 失败；资产扣减与道具消耗必须在同一逻辑边界内成对成功（先校验后扣）。
- **幂等**：所有发奖/领取（邮件附件 mail_claim、挂机 afk_claim、签到 sign_do、等级礼包、商城 mall_buy）必须写 `reward_log(transaction_id)` 防重；重复 transaction_id 直接返回上次结果，不二次发奖。
- **校验失败**：回包明确失败原因，客户端本地不扣资产。

### 3.4 字段纪律
- CS/SC 字段**只取自 `protocol/fields.json`**（经 proto_defs.py BY_CMD/MESSAGES 编码）；inventory 标「字段未知」的命令，handler 入参按现有 mock_server 解析逻辑为准，**不得自行补造字段名/类型**冒充原版。
- 新增字段需先反汇编对应 `cmd_resolve_*.luac` 或实机抓包取证，证据档至少 STRONG_INFERENCE 才允许写入。
