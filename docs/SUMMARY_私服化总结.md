# 绝世唐门 1.4.9 私服化 —— 总总结

> **文档目的**：总结本项目**全部修改方向**、**私服化制作的优缺点**、以及**走过的弯路与改正**。
> **事实纪律**：所有结论标【已确认】【已验证】【待验证】【未知】；**不把推测写成已确认**。
> **生成时间**：2026-09-18

## 一、项目定位（一句话）

**不是"做一个类似绝世唐门的游戏服务器"，而是"做一个能让原版绝世唐门 1.4.9 APK 继续运行的兼容服务器"。**

| 项 | 值 |
|---|---|
| 目标 APK | `anzbao/jstm.apk` — `com.shiyue.dldl.ewan.qihoo` / versionName **1.4.9** |
| 引擎 | Cocos2d-x 3.6 + **LuaJIT 2.0 字节码**（`1b 4c 4a`）【已验证】 |
| 线格式 | `[u32 BE payload_len][u16 BE cmd][body]`【已验证】 |
| 成功判据 | **`code == TRUE(1)`** 才是成功，否则 `message(msg)`【已确认】 |

---

## 二、★ 最高原则（贯穿始终的红线）

1. **原版 APK 是最终标准** —— 与任何参考项目冲突时，**APK 优先**
2. **参考项目只作架构参考**，禁止改名复制
3. **优先复用"架构思想"，谨慎复用代码**（逐一审计 LICENSE）
4. **不猜协议** —— 字段必须标 CONFIRMED / VERIFIED / INFERRED / UNKNOWN
5. **只操作自己的服务器**

**附加自定纪律**（实践中形成）：
- **先取证再改**；**一次一个变量**；**被否证的假设保留记录**（不删）
- **不编造数据**：无原版依据的数值一律标注"占位，待校准"
- **不重做客户端 UI**、**不自己发明协议**

## 四、★ 私服化制作的优缺点

### 4.1 优点

| # | 优点 | 说明 |
|---|---|---|
| 1 | **原版客户端可直接复用** | 无需重做 UI/资源/表现；**工作量集中在服务端** |
| 2 | **协议有权威来源** | `cmd_resolve_*.luac` 给出**3553 条字段定义**，不必猜 |
| 3 | **配置表可完整提取** | 347 张表 + 通用读取器 ⇒ 物品/任务/商城/技能数据**全部原版** |
| 4 | **单进程 Python + SQLite 已够用** | 实测中位延迟 **10.8~16.9 ms**；并发 200/200 成功 |
| 5 | **参考项目验证了架构方向** | ★ **kongkongxiyou 作者自己从多进程退回准单体** ⇒ 免费验证 JSTM 单进程路线 |
| 6 | **数据完整性可自动校验** | 无效 bid / item_id 重复 / None 字段 全部可脚本查 |
| 7 | **管理后台可运营调试** | 17+ 动作，含给物品/改等级/设任务/读配置 |

### 4.2 缺点 / 风险

| # | 缺点 | 说明 |
|---|---|---|
| 1 | **原版服务端数据不可得** | 战斗数值/怪物属性/限时任务等**存在取证天花板**，无法校准 |
| 2 | **客户端侧 bug 无法从服务端根治** | 如 `setSceneInfo` 写 R1 读 R0 的错位 ⇒ 只能靠探针绕过 |
| 3 | **协议字段"解而不全"** | 仍有含 `D\|Dsc*\|` 未解子表的 CMD（如 `19600/20100.promote`）⇒ 按纪律**不实现** |
| 4 | **单进程固有并发尾部** | 并发最大延迟 **1030 ms**（Python + GIL + SQLite 串行） |
| 5 | **参考项目代码一律不可复制** | 4 个无 LICENSE + 1 个 **GPL-3.0（大圣归来）**；**Survive 的 `aoi.h/astar.h/wordfilter.h` 文件头内嵌 GPLv3** |
| 6 | **真机多角色验证受阻** | `TcpHandler.cfg` 是**类属性全连接共享** ⇒ 全连接共用 `rid=1001` |
| 7 | **探针高频上报** | 某条上报累计数千次，需精简 |
| 8 | **部分场景无碰撞数据** | 90/124 场景无数据 ⇒ 保持 `allow_all` |

## 五、★★ 挫折与改正（如实记录，全部保留在案）

### 5.1 最大的一次：NPC 对话 **13 轮未闭环**

| 轮 | 当时认定的根因 | 实测结果 |
|---|---|---|
| 1-4 | `view.ctrl` 接错对象 / NPC 不在场 | ❌ 否证 |
| 5-9 | `getScene() == nil` | ⚠️ 是**症状**，非根因 |
| 10 | `self.ctrl` 为 nil | ❌ 实测是 **table** |
| 11 | 失败点回到 `getScene()` | ⚠️ 仍非根因 |
| **12** | **阻塞在 `skill_ctrl.luac` 抛的异常** | ✅ **正确** |
| **13** | `skill_ctrl.checkSkillEnable → kHaveSkill` 索引 nil | ✅ **精确到函数** |
| **14** | ★ **服务端发了**不存在的技能 bid `1001`**** | ✅ **✅ 修复成功** |

**最终根因（CONFIRMED）**：
```
config.json 的 skills = [{"bid": 1001}]
但客户端 Config.Skill 的真实 bid 是 [10000=普攻, 10001=逃跑, 10002=撤退, ...]
⇒ 不含 1001 ⇒ kHaveSkill 查 Config.Skill[1001] = nil
  ⇒ 索引 nil 抛异常 ⇒ 异常沿栈传播 ⇒ changeScene 中断
    ⇒ 场景初始化不完整 ⇒ NPC 对话失败
```
**修复**：`skills` 改为 `10000/10001/10002` ⇒ `sceneStart_oktrue`，异常栈消失 ⇒ **用户实机确认"能弹出对话了"** 🎉

**教训**：
- **症状 ≠ 根因**。前 11 轮都在追"场景字段"，真凶在**技能模块**。
- **必须用 `xpcall + debug.traceback` 抓真实调用栈** —— 静态反汇编到极限后，运行期取证才是终局手段。
- **服务端下发的 ID 必须校验存在性**（无效 ID 会引发客户端崩溃）。

## 六、★ 方法论教训（最有价值的部分）

1. **静态判据只能定"极性"，定不了"哪些值算阻挡"**
   —— 曾凭"NPC 坐标 + 邻接关系"把碰撞值 `2` 判成阻挡，**被真实运行轨迹否证**（11/387 真实坐标落在 `2` 上）。最终用 **387 个真实 `10204` 坐标**做回归门槛 ⇒ **误拦率 0.00%**。

2. **"更正不传播"是系统性风险**
   —— 同一错误（如"JSTM 有 20014 ACK 节流"）在多个文档间沿引，**订正只在局部完成却未传播**。已建立"待传播更正清单"。

3. **并发编辑同一文件极易互相覆盖**
   —— 多次出现 `file changed since it was read`。**约定：同一文件同一时间只由一人编辑**。

4. **`.get(k, default)` 对"存在但值为 None"的键返回 None**
   —— Python 陷阱，曾导致每 2.5 秒异常刷屏。

5. **验证脚本本身也会错**
   —— 偏移算错、空字节 falsy、`nonlocal` 误用 ⇒ **测试失败不等于产品失败**，必须先怀疑测试。

6. **★ 审计工具的"表示假设"必须跟着产物一起演进**（round38 / round41 各踩一次）
   —— 产物一变（`D|Dsc*|` 被展开成嵌套 `items`、默认应答带上 `msg` 文案），
   审计仍按旧表示算 ⇒ 一次冒出 144 条 / 26 条**假阳性**，几乎掩盖真问题。

7. **★ 两个独立审计给出不同结论时，先怀疑检查器**
   —— round41 出现"在线 107/107 一致"与"静态 26 条不一致"互相矛盾；
   按分工（在线=真解析、静态=算长度）立刻定位到静态侧的期望模型没跟上 `msg`。

8. **★ 包长是弱证据，定不了字段个数**
   —— `{bid}` 与 `{bid,num}` 对 8 字节 body 都"对得上"。
   **规格来源优先级：AutoConstruct spec > reader 原型 > 抓包长度**（round34→35 的教训）。

9. **★ 分发顺序：靠前的分支会"遮蔽"靠后的专用实现**
   —— 本轮又踩一次：`round39` 把 5 条排行榜并入通用零值集合，
   结果 round40 新写的**专用分支根本不执行**（五个榜全返回全零）。
   **约定：新增专用实现时，必须同时把它从通用集合移出。**

10. **★ 同族协议的"条目结构"并不一致，不能抽通用头部**
    —— `12901/12902/12911/12912` 的榜单项含 `career:u16`，
    **`12931` 没有 `career`**（只有 `lev:u8`）⇒ 抽通用 `_head()` 后 12931 多 2 字节。
    **逐条按 spec 编码**才安全。
