## 一、5 处改动汇总

### 改动 ①（S1-A-1）10300 handler 末尾排程补推

- **文件:行**：`server/mock_server.py`，10300 (CSRoleInit) handler 末尾（原 L17361–17363 → 新 L17417–17422）
- **改动内容**：在 `_mis_repush_at` 排程之后、`return` 之前，新增 5 行：
  ```python
  self._login_repush_at = time.time() + 5.0
  log('tcp.log', '  .. S1 风暴收尾补推已排程（+5s，10303/10306/13781/13786）')
  ```
- **原因**：登录风暴中 SC_10301（initRoleBaseData 重建 RoleVo，无 power 字段）晚于 SC_10303 到达；客户端角色面板在风暴中途对过渡态 vo 一次性快照定格 power=0 且不重渲染。需要在客户端初始化完毕后延迟 5s 触发补推。
- **字段证据来源**：C2.2 诊断（`docs/C2.2_实施记录.md`）；`attribute.service.role_power(cfg)` → `power_mod.calc_power(attr)`；既有 `_mis_repush_at` 心跳驱动模式（L9928–9940）。
- **diff 引用**：`docs/_raw/s1_a_diff.md` 改动 1。
- **验证结果**：tcp.log `[20:37:43] .. S1 风暴收尾补推已排程（+5s…）`；冷启动后角色面板综合战力=724112（非 0）。

### 改动 ②（S1-A-2）1199 心跳 handler 执行补推

- **文件:行**：`server/mock_server.py`，1199 心跳 handler（原 L9940 → 新 L9941–9994），位于 12400 补推块之后、15402 补推块之前。
- **改动内容**：检查 `_login_repush_at` 到期后推送 4 条：
  - SC_10303（204 bytes，复用 `build_10303(role_state, skills, attr)`，power 经 `role_power()` 真实计算=724112）
  - SC_10306（88 bytes，复用 `attr_table_10306(ad)` + `w_u16(mspd=100)` + `w_u32(power=724112)`，与 `attribute/handler.py` handle_10306 同构）
  - SC_13781（total_val=10，复用 `db_daily_get` + `richang_daily_tasks` + `db_daily_lingqu`，与 CS_13781 handler 同构）
  - SC_13786（richang=24，复用 `richang_daily_tasks` + `db_daily_get`，与 CS_13786 handler 同构）
  - 整体 try/except 包裹，失败仅记日志不崩溃。
- **原因**：心跳是"客户端已稳定"的最好信号；延迟 5s 确保 10301 重建 vo + 面板弹出快照完成后再补推。日常面板从不发 CS_13781/13786（tab 打开不发请求），服务端 handler 就绪无请求可应，故改为登录后主动补推。
- **字段证据来源**：10306 编码 = `attribute.service.attr_table_10306(ad)`（4×u16 + 12×u32 + 4×u16 + 4×u32）；13781/13786 数据源 = `db_daily_get(rid)` + `richang_daily_tasks()`；活力 total_val=10 来自 DB 真实任务进度求和（非硬编码）。
- **diff 引用**：`docs/_raw/s1_a_diff.md` 改动 2。
- **验证结果**：tcp.log `[20:37:43] << 10303 …(204 bytes)`、`<< 10306 mspd=100 power=724112(88 bytes)`、`<< 13781 total_val=10`、`<< 13786 richang=24`；重连后 20:38:55 再次触发。

### 改动 ③（S1-B-1）补推块内追加 10302（diamond）

- **文件:行**：`server/mock_server.py`，S1-A +5s 补推块内、10303 推送之后（L9952 起）。
- **改动内容**：
  ```python
  _pk2 = pack_frame(10302, build_10302(_st))
  self.request.sendall(_pk2)
  log('tcp.log', '  << 10302 SC_10302 资产刷新（S1-B 补 diamond=%s）(%d bytes)' % (_st.get('diamond', 0), len(_pk2)))
  ```

- **原因**：登录风暴只推 10301/10303/10305，从不推 10302；而 diamond 字段在 10302 的 1.4.11 尾部（build_10302 L5446-5448）⇒ 客户端登录后读不到 diamond ⇒ HUD 钻石停默认 0。`config_game_data.CodeToAssets` 共 41 项无 diamond 标签，故不能走 10305 增量表，只能走 10302 尾部。
- **字段证据来源**：`build_10302()`（L5413）尾部 `diamond:I`+`rainbow_diamond:I`（L5446-5448）；`_DB_TO_SC`（L5321）映射 `'diamond':'diamond'`；roles 表 diamond 列=0（真实存储）。
- **diff 引用**：`docs/_raw/s1_b_diff.md` A 段。

### 改动 ⑤（S1-B-3）11215 去掉 volume/volume_open 前缀

- **文件:行**：`server/partner/service.py`，`build_panel_11215`（L148 起）。
- **改动内容**：去掉 `w_u8(volume)+w_u8(volume_open)` 两字节前缀，只发 `w_u16(len(base))` 表计数。
- **原因**：1.4.9 `protocol/fields.json` SC_11215 = `partner_list:table` 直接以表计数(u16)开头，无前缀。旧码按 1.4.11 luac 格式补了两字节前缀 ⇒ 1.4.9 客户端把这两字节并进表计数、后续每个条目错位 2 字节 ⇒ 解析越界 ⇒ LUA ERROR [11215]（经 CS_10999 上报）。帧长印证：注释基线 2552 body = 2 + 53×48；旧码发 2554（多 2 字节）。
- **字段证据来源**：`protocol/fields.json`（1.4.9 权威）SC_11215 = partner_list:table；帧长 2552 vs 2554。
- **diff 引用**：`docs/_raw/s1_b_diff.md` B 段。
- **验证结果**：tcp.log `[20:37:32] << 11215 SC_11215 partner_list=53（partner.service 配置驱动）(2552 bytes)`（原 2554）；打开伙伴面板完整渲染，零 10999 上报。
