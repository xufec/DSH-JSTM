## 一、实施规范总纲（C1 第五步）

1. **先定位，再动手**：实现前先定位已有代码 / 资源 / 协议 / 数据；先明确需求与证据，再决定是否实现；优先复用现有客户端结构与资源，不重造。
2. **先证据后实现**：不能确认的状态标 UNKNOWN / STRONG_INFERENCE 并注明原因；禁止仅凭文件名、协议字段或图标认定功能已实现。
3. **服务端单一实现**：服务端统一使用 `server/mock_server.py`，不建第二套服务端实现。
4. **业务逻辑收口**：货币 / 奖励 / 背包 / 属性 / 战斗业务逻辑统一走 Service 层。
5. **禁止绕过校验**：禁止直改数据库绕过业务校验。
6. **禁止编造**：禁止编造原版协议 / 剧情 / 道具属性 / 数值；一切推断必须显式标记（STRONG_INFERENCE / INFERENCE）。
7. **改前评估影响面**：修改前检查调用链与影响范围，避免破坏已有登录 / 地图 / 角色 / 任务功能。
8. **完成标准**：每阶段必须有可重复测试步骤、实际日志与验收结果；不以"代码已生成"为完成标准。

## 二、状态分类（A-F）判定规则

| 类别 | 含义 | 程序化初判规则 |
|---|---|---|
| A | 已验证可用 | `impl_status=已实现` 且 `evidence_tier=VERIFIED`，或 HANDOFF/tests 回归证实闭环 |
| B | 已实现未完整验证 | `impl_status=已实现` 但 `evidence_tier≠VERIFIED`（有 mock_server 行号/模块，缺实机或回归验证） |
| C | 客户端有界面业务不完整 | ui_inventory 有 A/B 类界面（模块+资源齐备）但 matrix `impl_status=部分实现/未实现` |
| D | 只有资源配置或协议证据 | ui_inventory C 类（仅图标）或仅 data/protocol 证据，无实现、无完整 UI |
| E | 尚未发现可靠证据 | C0 unknown_inventory 名单 9 系统或 `evidence_tier=UNKNOWN` / present_in 全 UNKNOWN |
| F | 暂不恢复或等待依赖完成 | ui_inventory D 类（已废弃/被替换）、或依赖系统缺失、或明确优先级低 |

判定优先级（自上而下，先命中先归类）：E → A → B → C → F → D。边界冲突时以证据为准，判定理由见第六节清单。
