## 三、★ 架构决策与分析

### 决策 1：**保持单进程，不做多进程/网关分层**

| 论据 | 来源 |
|---|---|
| ★ **kongkongxiyou 作者自己从多进程退回准单体**（6 类进程 → 12 场景挤 1 个 area-server；chat/path/fight 未部署；留 `handleRemote` 适配层把跨进程调用收敛为单进程函数调用） | 五项目审计【已验证】 |
| JSTM 是**私服**，不是商业服；并发量级不同 | 定位 |
| 单进程实测中位延迟 **10.8~16.9 ms**，够用 | 性能基准【已验证】 |
| 多进程会引入：进程间状态同步、序列化开销、调试复杂度 | 工程判断 |

**⇒ 结论：单进程是**合理**的，不是妥协。**
**⚠️ 代价**：并发尾部 1030 ms（Python + GIL + SQLite 串行）—— 如实记录，非本次引入。

### 决策 2：**Protocol Adapter 与 Game Core 解耦**

```
现状：mock_server.py 已是这个形态（pack_frame + cmd 分支 + DB）
      ⇒ 不是从零开始，而是"已有 Adapter 雏形"
改进方向：把单文件 if 链按域拆 handler
          （借鉴 kongkongxiyou 的 area/handler/*Handler.js）
```

### 决策 3：**AOI/寻路自研，不复制参考代码**

**原因（LICENSE）**【已验证】：
```
Survive 的 common/aoi.h、common/astar.h、common/wordfilter.h
  **文件头内嵌 GPLv3 全文声明**
  ⇒ 连"翻译成 Python"都有风险
kongkongxiyou 的 pomelo-aoi/pathfinding/bt 插件
  **未随 ZIP 打包**（22486 文件搜索 0 命中）
  ⇒ 只有"调用契约"，内核读不到
```
**⇒ 只能读"设计思想"，实现**完全自写**。**

**JSTM 的三处超越**：
1. **精确圆判定**取代同塔近似
2. **AOI 只返回 uid，绝不碰 socket**
3. **★ L1/L2 安全校验（参考项目全部缺失）**

### 决策 4：**战斗服务端自定节拍**

**分析**（★ 一次重大更正）：
```
❌ 我曾判断："JSTM 服务端推 SC_20012/20013 → 客户端 CS_20014 ACK → 推进"
   依据：battle_chain_verified.md —— 但那份文档描述的是**我们自己 mock_server 的实现**
   （行 2445 if cmd == 20014:），**不是真机客户端行为**！

✅ 真机取证：客户端 **从不发 CS_20011/CS_20014**（4 场完整捕获零次）
   ⇒ 服务端**必须自定节拍**（现 2.5 秒/回合自续期）
```
**⇒ "回合节奏所有权相反"不成立；"照搬 CXEngine 会丢 ACK 节流"作废（没有节流可丢）。**

**★ 不能照搬 CXEngine 的**真正理由**（5 条字段级证据）**：
1. JSTM `SC_20010` 有**阵法 + 回合波次 + 观战 + effect_id**，CXEngine `BattleMT:Serialize()` 只有 `{id, team_type, pos_id}` ⇒ **表达不了 JSTM 的一回合**
2. JSTM **每回合全量重推单位状态**（`summon_play` 16 字段），CXEngine **无重推机制**
3. 线格式不同（`[u32BE][u16BE][二进制]` vs `[LE][LE][JSON]`）
4. JSTM 独有 4 套子系统：观战(`20016/17`)、录像(`20025–20030`)、自动战斗、客户端演算校验
5. 安全模型与数值内容不可复用（CXEngine 数值**全是《梦幻西游》的**）

**⇒ 一句话：不是"节奏对不上"，而是"CXEngine 的战斗对象比 JSTM 少了一半字段"，照搬会丢字段。**

### 决策 5：**属性系统应"只存输入 + 派生重算"**（⚠️ 未落地）

**Survive 的三条铁律**（唯一最佳实践）：
```
① 只持久化**输入项**（attr_db_save = attack-1 = **23**）
   派生属性每次登录 CalAttr **全量重算**
② 变更 → 发信号 → 重算（bag:Swap 返回 "recalattr" → CalAttr(true)）
③ **可见性白名单**（attr2view = {level, life, maxlife} 只 3 个）
   + 一次变更发"视野包 + 自身包"
```

**JSTM 现状（⚠️ 缺陷）**：
```
role_attr 只有 26 列（25 属性 + rid）
而属性系统 AttrLen = 64
⇒ **既存了 21 个派生项（不该存）、又漏了 39 个属性**
⇒ 同源问题："按当前实现需要逐列加，没按属性总表设计"
```

**JSTM 已具备落地条件**：
- `AttrKeyIsShow` 配置**已存在**（可见性白名单）
- `Config.RoleAttr` 表已提取
- `role_assets` 通用容器已就绪

**⇒ 这是本项目唯一的 P0 数据模型缺口。**

### 5.3 ★ "综合战力为 0" 的深入分析（当前最大未解）

**已确证**：
```
① 客户端"变强面板" advance_new_panel proto[20] 读：
     vo = GameData:getRoleVo()
     vo.power_value:setString(vo.power[1].val)     ← 综合战力
     vo.tui_power:setString(vo.power[2].val)       ← 推荐战力
② advanace_new_panel 里**没有直接 TSETS 'power'** ⇒ power 是 RoleVo 属性
③ RoleVo.setRoleAttribute(attrId, val) 是唯一写入器
④ ★ 运行时探针（包 setRoleAttribute）：**power/atk_s/hp_max 从未被写入**
```

**已实现但未被采用**：
```
10304（SC_10304{... power:u32, attr:table(24 项)}） ← 服务端已发 power=160095
20100（SC_20100{power:table(code,val), promote}）  ← 服务端已发 power=160095
```

**⇒ 分析结论**：存在一条**"角色属性同步消息"**，带 `power`（**数组**），通过
`setRoleAttribute('power', ...)` 写入 RoleVo —— **该消息未定位**。
10304 的标量 power 与 20100 的分量列表**都不是**面板读的那个数组。

**下一步方向**：追 `setRoleAttribute('power', ...)` 的调用链来源（服务端正解，需 1-2 轮）。

## 六、★ 风险分析

| 风险 | 等级 | 说明 | 缓解 |
|---|---|---|---|
| **原版服务端数据不可得** | 🔴 高 | 战斗数值/怪物属性无法校准 | 数值标"占位"；用真实轨迹做回归门槛 |

## 八、★ 架构层面的最终建议

1. **不要因为参考项目是"多进程/C+Lua/MySQL"就改 JSTM 形态**
   —— JSTM 的形态（单进程 Python + SQLite）**已够用且已验证**

2. **改进方向是"功能补齐"，不是"架构重构"**
   —— 真正缺的是 AOI/寻路（**已补**）、技能、副本

3. **优先做"只存输入 + 派生重算"**
   —— 这是数据不腐化的底线（Survive 唯一最佳实践）

4. **把 `mock_server.py` 的 if 链按域拆 handler**
   —— **7265 行**已远超维护上限（round42 抽 `shop_try_buy()` 是正确方向：
   三个购买入口共用一处实现，避免各自漂移）

5. **建立"协议单一真源"** ✅ **已部分落地**
   —— 以 `protocol/fields.json` 为唯一真源生成 `proto_defs.py`
   （`gen_proto_defs.py` 已存在）；
   **并已加"第二路径审计"作为 CI 级校验**：`audit_specs_vs_fields.py` 用
   AutoConstruct 调用点独立还原 2463 条规格与 `fields.json` 比对 ⇒ **0 不一致**。
   `fields.json` 本身也已自洽化（`resolve_dsc_refs.py`，302 修正 + 346 展开）。

6. **坚持分级标注**
   —— 本项目最大的资产是"**3553 条定义 + 347 配置表 + 四道自动审计 + 全量零不一致**"，
   **最大的风险依然是"以为已验证，其实是推测"** ——
   round34 的 `CS_16603` 误订正就是活例（包长看着像铁证，实为 4 字节缓冲区残留）。
   现在这条风险由 `replay_captures.py`（真机 876 变体回放）持续兜住。
