## §2 统一战力展示核验

### 2.1 角色面板战力来源
- **数据通道**：SC_10303「自己角色面板属性」携带 `power:uint32` + `attr:table`；SC_10306 携带 `attr:table, mspd, power`；SC_10301 提供基础信息。登录链 10300 RoleInit → push 资产/属性。
- **服务端计算**：`power/service`（AttrPower 31 属性 CONFIRMED，见 C1）；属性表 `server/_attr_data.json` AttrLen=64 CONFIRMED（HANDOVER P0#2）。属性/战力变动走 `attribute.service + power.service` 重算后，由 `SessionRegistry.push_to_rid` 关联增量推送（SC_10301 属性 / SC_10303 资产 / SC_10502 背包 / SC_10304 战力）。

### 2.2 各养成系统面板战力是否同一来源
- 翅膀 CS_11600 自带 `power:uint32`；光环 CS_19100 自带 `power:uint32`；神器面板显示总战力 1959/战力 1395；神格面板战力 750。
- 这些是**各系统自身的战力分项**，最终应汇总进角色总战力（实机 HUD=724112）。服务端重算链一致（attribute/power service），即「服务端侧是同一来源」。

### 2.3 F1 首帧时序影响范围
- 角色面板首开(01)综合战力=0、装备格空占位；重开(08)即显 724112；**HUD 右上角全程 724112**——说明 HUD 读的是登录即达的 10303 缓存，而面板 onEnter 渲染早于 10304/装备属性到达。
- 锻造「当前装备秘银长枪属性=0、升级预览 213 正常」与 F1 同源：锻造视图未在首帧读到已穿戴装备实例属性。
- 影响范围：角色面板首帧、锻造当前装备视图首帧；不影响 HUD、不影响重开后渲染、不持久化。

### 2.4 结论
1. **服务端侧存在统一属性/战力计算**：`server/attribute/` + `server/power/`（AttrPower 31 属性 CONFIRMED，`_attr_data.json` AttrLen=64 CONFIRMED），各养成系统属性变动均回流此链并回推 SC_10304。
2. **客户端侧战力显示闭环未打通**：`advance_new_panel` 读 `RoleVo.power[1].val`，运行时探针证明**从无消息写入 RoleVo.power**；10304/20100 服务端已实现但**未被客户端采用**（HANDOVER P0#1）。这是 F1 的根因，不是数值算错。
3. **口径矛盾（需标注，不编造）**：protocol_inventory 将 10304 命名为「别人角色面板属性」，而 C1/HANDOVER 实际把它当「SC_10304 战力同步通道」使用。二者字段结构相同（rid/…/power/attr）；恢复时应以「10304=战力同步通道」为准，并补齐客户端对 RoleVo.power 的写入消费。
4. **界面硬编码/矛盾数值**：锻造当前装备属性 0 vs 升级预览 213 属时序（非硬编码）；各养成面板战力分项与总战力 724112 的**汇总对账**在客户端未闭环，待 F1 修复后回归核对。
