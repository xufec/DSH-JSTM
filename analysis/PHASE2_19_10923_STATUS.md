# PHASE 2.19 —— `10923` 单个活动状态：`status` 从恒 0 改为**有据取值**

> 选靶依据：`10923` 客户端**真实调用 73 次**（活动族里仅次于 16605/10924/10922），
> 而原实现**恒回 `status=0`** —— 按 R49 查明且记录在案的语义，**`status != 1` 时客户端不显示该图标**。

## 一、证据链（不编造，全部可追溯）

| # | 证据 | 出处 |
|---|---|---|
| ① | `10922/10923/10924/10925` **共用同一客户端处理体** `Activityhander10925`；条目结构一致；门槛为 `Config.Function[id]` 存在 **且 `is_open==1` 且 `open_lev <= 角色等级`** | 反汇编 `activity_ctrl.luac`（proto#27/#29/#30），见 `analysis/extraction/real_cs_formats_1_4_11.md` §6.3/§6.5 |
| ② | 客户端 **proto#49 要求 `status == 1` 才显示图标**（`{501,502,503,504}` 的检查） | `mock_server.py` L17550（R49 查明并记录）|
| ③ | 现存 `10924` 实现本就对合格条目发 **`status=1` + `int_args=[时间戳]`**（空 `int_args` 会让 `daily_ctrl` 崩溃）| `mock_server.py` L17553 |

⇒ 因此 `10923` 的 `status` 应取 **1（合格）/ 0（不合格）**，`int_args` 取 **`[当前时间戳]`（合格时）**，
与**已上线的 10924 行为保持一致**。

```python
aid = CS.id  (u16)

SC_10923 = {id:u16, status:u8, int_args:table(val:u32)}
```

## 四、★ 过程中我引入并**立即修掉**的一个回归（如实记录）

我最初**同时**给 `10925` 也加了一个新分支（理由是 §6.5 说 10923/10925 同构）。


查明：`10925` **早已有分支**（`L18394` 的 `if cmd in (13781,13786,13787,13788,13789,10925)`），

> **教训**：给一条命令加专用分支前，**必须先 `Select-String` 确认旧链里没有同名分支** ——
