## 一、根因定位（证据链完整）

### 1.1 客户端期望（反汇编 `daily_ctrl.luac`，见 `analysis/_daily_ctrl.txt`）

| proto | 关键字符串 | 行为 |
|---|---|---|
| #11 `DATA_CHANGE` | `total_huoli` / `cur_huoli` / `max_count` / `total` / `setTotalHuoli` / `setCurHuoli` | 遍历内部数据表，**累加每项的 `total_huoli`/`cur_huoli`**，再 `setTotalHuoli/setCurHuoli` |
| #12 `getTotalHuoli` | `HuoliClearVal2` / `Config` / `lev` / `getRoleVo` | `Config.HuoliClearVal2[角色等级]` 与当前 total 比较 |
| #2x `updateHuoli` | `huoli_list` / `updateHuoli` / `data` | 用 SC 的 `huoli_list` 构建内部数据表 |

### 1.2 服务端下发的内容（实测）

`server/_richang.json` 里 `type_name == '日常任务'` 共 **24** 条，其中带 `huoli_id` 的 **12** 条会被写进 `huoli_list`（其余 `huoli_id=0` 跳过）。

### 1.3 冲突点 ★

客户端配置 `config_richang.Huoli` 按 `huoli_id` 带 **`limit_lev`（等级门槛）**：

| huoli_id | name | limit_lev | 玩家等级 70 ⇒ |
|---|---|---|---|
| 255 | 困神塔 | **90** | **未开放** |
| 其它 11 个 | — | ≤ 45 | 已开放 |

而服务端 `richang_daily_tasks()` **没有任何等级过滤**，把 `huoli_id=255`（门槛 90）也发下去了。

⇒ 客户端按 70 级在 `Huoli[255].total_huoli[band]` 里**取不到 band**，该表项累加为 nil
⇒ `DATA_CHANGE` 的合计变成 nil ⇒ 面板「拥有活力」显示 **`????/????`**。

> 双证：MuMu 实机截图 + `ocr_image` 两次独立读取均为 `????/????`（排除了"视觉模型读不出小字"的可能）。
