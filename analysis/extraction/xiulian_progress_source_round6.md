# 修炼面板数值来源：控制实验与**阴性结论**（第 6 轮）

> 本轮**不留任何代码改动**：实验用的 `server/config.json` 已按备份逐字节还原（diff = 0）。
> 目的：判定「修炼面板的 35/50 与 消耗/拥有 到底由哪个字段驱动」。

---

## 一、实验设计（单变量、可判真伪）

| 项 | 设置 |
|---|---|
| 自变量 | `server/config.json` → `skills[bid=10822].exp`：**35 → 41** |
| 期望 | 若面板读该字段 ⇒「修炼进度」应显示 **41/50** |
| 控制 | 改完重启服务端；**冷启客户端**（force-stop + start）后再开 魂技→修炼 |
| 读数 | ① 服务端 `/DSH_ADMIN/power.attrs.practice_exp` ② 面板 OCR |

## 二、服务端侧：派生链**双向验证通过**（CONFIRMED）

代码依据（既有的项目实现）：

- `server/role/storage.py:160-166` —— `st['practice_exp'] = int(_sk.get('exp', 0))`，
  `_sk` = `config.json:skills` 里 `bid=10822` 那条；
- `server/mock_server.py:149-154` —— 同源动态读取（注释自述 "same src as 10621 skill_list"）。

实测三态：

| 状态 | `config.json:10822.exp` | `/DSH_ADMIN/power → practice_exp` |
|---|---|---|
| A（实验态） | **41** | **41** ✅ |
| B（再确认） | 41 | **41** ✅ |
| C（还原后） | **35** | **35** ✅ |

⇒ **`config.json:10822.exp` → `practice_exp` 这条链确实成立且可双向驱动**（服务端侧）。

---

## 三、客户端侧：面板**不跟随**该字段（**阴性结论，CONFIRMED**）

在服务端 `practice_exp = 41`（且 `SC_10621` 的 10822 exp = 41）的情况下，
**冷启客户端** → 魂技 → 修炼，OCR 仍是：

```
修炼进度: 35/50
消耗: EXP
拥有: EXP
抗控修炼 LV. 22
```

且该截图与"exp=35 时"的截图**字节数完全相同**（均 1,300,946 B）⇒ 画面逐像素一致。

⇒ **面板显示的 35 与 消耗/拥有 不由服务端 `practice_exp` / `SC_10621.skill_list.exp` 驱动。**

### 这也**否证**了 HANDOFF 里的一个假设

HANDOFF 缺口 #5 曾写「practice_exp 已改动态读取=35，**待用户二次回证是否上屏**」。
本控制实验给出明确答复：**没有上屏**——该字段不是面板那个 35 的来源。
（此前几轮用 OCR 只能说"仍空白"，本轮用**改变量 + 冷启**把因果钉死了。）

## 四、推论与下一步（**不再猜字段**）

**STRONG_INFERENCE**：「修炼进度 / 消耗 / 拥有」三者同源，来自
**客户端本地数据**（本地存档 / 客户端自算）或**另一条我们还没识别的帧**；
而我们一直在驱动的 `practice_exp`（以及 `10621.skill_list`）与它们**不是同一条数据流**。

三条可判真伪的取证路径（按性价比排序）：

| # | 路径 | 能判什么 |
|---|---|---|
| 1 | **frida hook** 面板的取数函数（`daily`/`技能`视图的 `setXxx`） | 直接看到它读的是哪个全局/哪张表 → 一锤定音 |
| 2 | **找到承载 35 的帧**：把所有下发的 SC 逐帧与面板值对照（含 10304/10306 推送） | 若某帧里出现 35 且改它 UI 跟随 ⇒ 找到真源 |
| 3 | **真服对照**：一次真服的登录/进修炼面板流量 | 权威源，一次比对即可定位 |

> 注：路径 1 需要授权调用项目里的 frida 工具链；路径 2 纯只读即可做，但需要**逐帧回放+UI 观察**的组合，工作量较大。
