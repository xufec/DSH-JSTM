# 战斗族（20002 族）下沉注册方案设计

> 日期：2026-10-02 05:25 UTC+8。纯设计，不落代码。
> 前置状态：AOI 推送 + 战斗 Timer 回调均已收敛到 push_to_rid 投递（见 aoi_battle_down_sink.md §6）。
> 断点原因：20002/20010/20012/20013/20020/20023/20021 帧在 threading.Timer 异步线程产出，单客户端帧间时序难逐字节固定。

## 1. 时序锚点固定方案

异步帧时序漂移的本质：Timer 线程产出帧的**间隔**随系统负载抖动，但每帧的**内容字节**由战斗状态机确定性决定（mon hp/回合数/结果固定）。因此对比应锚定**帧内容**而非帧间间隔。

三个候选方案（按可靠性排序）：

### 方案 A：服务端确定性重放端点（推荐，解锁后首选）
- 在 /DSH_ADMIN 加一个只读/受控动作：`/DSH_ADMIN/battle_replay?mon_id=X&seed=Y`，服务端用固定 seed 构造一次战斗（JSTM 模型 + 固定 rand seed），跑完整个 20002→20010→…→20023 链，把**每帧内容**落 logs/battle_replay.log（命令号+hex bytes）。
- 改前跑一次存 baseline hex；改后跑同 seed 再存 hex；逐命令对比 hex（剔除时间戳字段，若有）。
- 优点：不依赖在线客户端、可重复、锚点完全固定、CI 可跑。
- 缺点：需新增受控 GM 端点（写路径小，但隔离在 admin 路由，不进游戏链）。

### 方案 B：帧内容对比（命令帧本身，不对比时序）
- 实机触发一次战斗，抓 tcp.log 里 20002/20010/20012/20013/20020/20023 各帧的字节长度 + 关键字段（result/round/mon_id）。
- 改前/改后各抓一次，对比**同命令号帧的字节内容**（忽略帧到达先后与间隔）。
- 优点：无需新端点。
- 缺点：单客户端战斗结果依赖随机数，需固定 mon_id 且接受 TEST_ONLY 数值；帧数量（20012/20013×N）随回合数变化——需固定回合数或容忍 N 漂移。

### 方案 C：第二在线客户端协同（双端抓帧互证）
- 第二个客户端（小号/模拟器双开）同场景同时战斗，双端 tcp.log 互证帧序列一致。
- 优点：最接近真实。
- 缺点：需第二客户端在线，环境成本高，本批无。

## 2. 注册步骤（每步可回滚）
1. **抽 handler**：20002 入口（mock_server L16797）→ battle_service/handler.py。依赖：battle_mod、role_state、pack_frame。先只搬入口，注册 20002，旧 if 块注释保留。
2. **字节对比**：方案 A 重放端点改前/改后 hex 对比 20002/20010。
3. **逐命令注册**：20010→20014（回合驱动）→20021（关结束界面）。每步 hex 对比。
4. **Timer 回调不动**：_battle_push_round/_battle_settle 已收敛 push_to_rid，保持现状。
- 回滚条件：任一命令帧 hex 非空 diff → 立即注释新 handler、恢复旧 if 块、重启，记录差异。

## 3. 风险评估
- **Timer 竞态**：push_to_rid 持 LIVE_LOCK 快照连接列表，与 Timer 线程产出帧解耦——已安全。
- **帧序漂移**：客户端按命令号区分帧（20012 vs 20013），顺序由状态机决定，注册入口不改状态机 ⇒ 无漂移。
- **旧链兼容**：注册后 dispatch.handle 先截胡，旧 if 块注释保留；若 handler 异常返回 None 则回落旧链（兼容层语义）。

## 4. 结论
**当前单客户端环境：不可安全注册。** 依据：
- 单客户端战斗帧的回合数 N 与随机结果不可固定，逐字节对比锚点不稳。
- 无确定性重放端点（方案 A 未建）。

**解锁前置（按优先级）**：
1. 建 /DSH_ADMIN/battle_replay 确定性重放端点（方案 A）——建后即可安全注册，CI 可跑。
2. 或：第二在线客户端 + 固定 mon_id 战斗（方案 C）。
3. 短期可接受方案 B（帧内容+关键字段对比，容忍 N 漂移）做冒烟验证。
