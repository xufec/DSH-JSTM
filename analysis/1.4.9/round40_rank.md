## 二、★ 踩到的两个坑（都值得记录）

### 2.1 分发顺序陷阱：被 round39 自己加的集合"遮蔽"

第一版实现后验证发现：**五个榜全都返回了全零**。

原因：round39 把这 5 条按"查询型 GAP"并入了 `_GENERIC_DEFAULT_CMDS`，
而**通用分支位置靠前**，抢先返回了零值 —— 我的专用分支根本没执行。
（`_GENERIC_DEFAULT_CMDS` 的注释里早就写过这个陷阱，round31/32/33/34 都踩过。）

⇒ **修正：这 5 条必须从通用集合移出**。移出后 `SC_12901` 立刻从 9 字节（全零）
变成 113 字节（真实数据）。

### 2.2 逐榜条目结构并不一致：12931 没有 `career`

`_head()` 起初按 12901 的布局写了 `career:u16`，结果 12931 多出 2 字节：

```
SC_12931  len=28  解析消耗=26  FAIL
```

回到 `cmd_resolve_129.luac` 权威 spec 复核：

| 榜单 | `rank_list` 条目 |
|---|---|
| 12901 / 12902 / 12911 / 12912 | `ord, rid, srv_id, name, sex, **career:u16**, val` |
| **12931** | `ord, rid, srv_id, name, sex, **lev:u8**, val` （**无 career**） |

⇒ **同一"排行榜族"里每个榜的条目字段并不相同**，必须逐条按 spec 编码，
不能抽一个通用头部了事。修正后 12931 = 26 字节，精确消耗。

## 三、诚实性论证（为什么可以这样回）

1. **"自己是第 1 名"是真话**：本服 DB 里只有 1 个角色（`roles` 表 1 行）
   ⇒ 该角色在该榜上确实是 1/1 名。
2. **战力值算法与 10304 完全同源**：抽出 `role_attr_dict(cfg)` / `role_power(cfg)`
   两个模块级函数，10304（角色属性大包）与 12901（战力榜）**调用同一函数**，
   避免"两个面板显示两个战力"。
3. **9 项战力构成只填 `power_eqm_role` 是真实分解**：本服战力**完全**由角色属性/装备
   经 `power_mod.calc_power()` 算出，**没有**建模技能 / 英雄 / 坐骑 / 灵兽 / 神器 /
   翅膀 / 法宝 等系统的独立战力 ⇒ 其余 8 项为 0 是事实，不是占位。

## 四、为什么 12902 / 12911 / 12912 回空榜

`config_rank.luac` 是榜单配置（48 条），每条 = `{cmd, type, title, chId, sId, iconId}`：

```
12901 → type=101 title=12 | 12902 → 102/9 | 12911 → 201/10
12912 → 202/11            | 12931 → 301/1
```

**榜名是资源 id（`title`），配置里没有任何名称字符串**；
而资源清单 `all_res_file.luac` **不是 LuaJIT dump**（`BCError: not a LuaJIT dump`），
无法据此解出榜名 ⇒ **这 3 个榜的指标（`val` 的含义）无法取证**。

按项目纪律（不猜数值），这 3 个回**空榜**——"暂无数据"是真话，
比编一个数值诚实，也比无应答（客户端等不到）好。

> 这 3 条从"通用零值"变成了"专用空榜"，**指标语义上有明确边界**：
> 若将来解出榜名（例如从 Android 资源表或另一份未加密清单），只需在
> `elif cmd == ...` 里补上该榜的 `val` 取值即可。
