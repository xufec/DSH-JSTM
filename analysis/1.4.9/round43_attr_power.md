## 二、★ 发现 1：`SC_10306` 的条目结构与 `SC_10304` **并不相同**

权威 spec（`cmd_resolve_103.luac` AutoConstruct）逐项核对：

| 消息 | `attr` 条目类型序列 | 条目字节 | 整包 |
|---|---|---|---|
| `SC_10304` | `H H H H` + **20×I** | 88 | 182 |
| **`SC_10306`** | `H H H H` + **12×I** + `H H H H` + `4×I` | **80** | **88** |

差别就在 **`atk_abs / def_abs / reduce / hurt` 这 4 项**：
在 10304 里是 **u32**，在 10306 里是 **u16**。

**原实现直接复用了 10304 的 `ATTR_KEYS[:4] / [4:]` 切分** ⇒ 10306 应答多写 **8 字节**
（96 而非 88）⇒ 客户端把 `mspd`、`power` 从错误偏移读走 ⇒ **战力依然写不进面板**。

> 这与 round40 的 `12931`（同族榜单项少了 `career`）是**同一类错误**：
> **"同族"不等于"同构"**。已把两个消息的编码器**各自独立**
> （`attr_table_10304()` / `attr_table_10306()`），从代码层面钉死。

### ★ 顺带暴露：一个**审计盲区**

`10306` 既**不在** `_GENERIC_DEFAULT_CMDS` / `_UNSUPPORTED_ACTION_CMDS`（走专用分支），
真机 341 个抓包里也**一次没发过** ⇒ **静态审计与回放审计都覆盖不到它**。

> ⇒ 建立待办：审计需要覆盖"**专用 handler 且真机没发过**"的命令
> （做法：列出全部专用分支中 CS 为空的查询型命令，逐一按规格校验应答）。
> 本轮的 `verify_attr_power.py` 是该思路的一个点状实现。

## 三、★ 发现 2：`10306` 才是写 `RoleVo.power` 的同步包（推翻旧结论）

旧文档（`SUMMARY` §5.4 / `ARCHITECTURE` §5.3）写的是：
> "综合战力面板读 `RoleVo.power`，运行时探针证明**从未被任何消息写入** ⇒ 存在一条未定位的同步消息"

本轮取证更新：

| 证据 | 结果 |
|---|---|
| `SC_10306` 权威 spec | `attr:表(24项) + mspd:u16 + power:u32` —— **含 power** |
| 客户端 `role_ctrl` | 同时注册 `sender10306` 与 `rgp_hander10306` ⇒ **能发也能收** |
| 真机 341 个抓包 | **10306 出现 0 次** |

**修正后的结论**：不是"没有这条消息"，而是**真机没打开"变强面板"所以没发**。
服务端此前对 10306 无应答 ⇒ 即便开了面板也拿不到 power。
⇒ 并行会话已把 10306 实现，本轮又修掉了它的**结构错位**，这条链路现在是通的。

## 四、口径统一：4 处战力计算 → **1 处**

改前存在**四套**战力算法/属性来源：

| 位置 | 原做法 | 问题 |
|---|---|---|
| `SC_10304` | `role_power(cfg)` | ✅ 已是基准 |
| `SC_10306` | `role_power(cfg)` + **错误的 attr 切分** | 结构错位（见 §二） |
| `SC_20100` | **自建 16 项默认属性表** + 直接 `calc_power` | 与 `ATTR_DEFAULTS`(24 项) **两份默认集**，迟早漂移 |
| `admin /power` | 读 `role_state`（DB 状态）+ **自选 18 项键表** | **数据源都不同** ⇒ HTTP 看到的战力与游戏内可能不一致 |

**改后**：全文件只剩 `role_power()` 内部**一处** `power_mod.calc_power` 调用
（`grep power_mod.calc_power` 仅剩定义处，其余全是注释）。

- `SC_20100` → `power_total = role_power(self.cfg)`
- `admin /power` → 总战力走 `role_power()`，**明细用同一份属性字典**算，保证"明细之和 == 总值"

## 五、★ 64 项属性 vs `role_attr` 的差异清单（新增交付物）

`tools/gen_attr_meta.py` → `server/_attr_meta.json`

```
AttrLen=64 ｜ role_attr 列 26 ｜ 缺列 40（其中**带战力权重**的 10 项）
```

**★ 缺失且带战力权重 —— 直接导致战力算少**：

| id | key | 中文 | 权重 |
|---|---|---|---|
| 131 | `control` | 控制等级 | 90 |
| 132 | `anti_control` | 抗控等级 | 90 |
| 142 | `atk_abs_s` | 物理绝对攻击 | 41 |
| 143 | `atk_abs_p` | 法术绝对攻击 | 41 |
| 144 | `def_abs_s` | 物理绝对防御 | 41 |
| 145 | `def_abs_p` | 法术绝对防御 | 41 |
| 240-243 | `anti_control_s/c/m/y` | 抗睡眠/嘲讽/沉默/眩晕 | 各 30 |

⇒ **这就是"我们的战力与原版对不上"的可量化原因**：
`AttrPower` 里有权重、但 `role_attr` 没落这 10 列 ⇒ `calc_power` 里它们恒为 0。

> ⚠ 按决策 #4（**严格不猜**）：这些列**不补零占位**（补 0 与不补在数值上等价，
> 却会给人"已实现"的错觉）。正确做法是等**真实来源**（装备/养成系统的属性计算）
> 到位后再落库 —— 列为后续轮次事项。

**其它缺失项（权重为 0，只影响展示）**：
`hp`(当前血量·运行时)、`energy*`(士气)、`hit_rate/crit_rate/dodge_rate/tenacity_rate`(真值率)、
`reduce_s/p`、`hurt_s/p`、`be_hurt*`、`res*`、`dam*`、`crit_hurt`、`crit_reduce`、
`red_tar_def_*`、`dmg_back`、`anger_start`、`cure/be_cure`、**`mspd`**(移动速度)。

**可取证为"派生"的展示副本**（`src=derived`，同表内成对存在）：

```
hit_rate_show(201) ← hit_rate(125)      dodge_rate_show(202) ← dodge_rate(138)
crit_rate_show(203) ← crit_rate(126)    tenacity_rate_show(204) ← tenacity_rate(139)
```

`src` 只标**有证据**的：`derived`(4 项，见上) / `runtime`(`hp`) / 其余一律 **`unknown`**（不猜）。

**顺带发现**：`mspd`（移动速度，id=130）**不在 `role_attr`**，
而 `roles` 表也没有该列 ⇒ `SC_10304/10306` 的 `mspd` **恒发 0**。
该属性战力权重为 0，不影响战力，但**影响客户端移动表现** ⇒ 记为后续小项。
