## 一、先说结论

**`+-0123456789` 不是我们下发的数据，而是客户端自己的 `TextAtlas` 占位字符串。**

证据（反汇编 `assets/src/game/form/form_pos_item.luac proto[2]`）：

```lua
@67  ccui.TextAtlas              -- 创建数字标签
@72  self.pos_num = ccui.TextAtlas:create(...)
@73  getNumberSize('num1')
@78  self.pos_num:setProperty(
@79      '+-0123456789',                 -- ← stringValue（要显示的文本）
@81      PathTool.getNumberRes('num1'),  -- ← 数字图集（num1.png）
@85      W, H,
@86      '.')                            -- ← startCharMap 分隔符
```

`assets/src/game/title/title_view.luac proto[2] @177` 里是同一形态：

```lua
ccui.TextAtlas:create('+-0123456789', PathTool.getNumberRes('num1'), W, H, '.')
```

**⇒ `'+-0123456789'` 是"先把数字图集里全部字形预加载"用的初始字符串
（Cocos 的常见写法），随后应由 `setString(真实值)` 覆盖。**

**⇒ 画面上一直显示它，说明这些 label 没有被写入真实值（`setString` 未生效）。**

## 四、为什么没被填上（推断，已标注为推断）

这些 label 的值来自**装备/称号等数据**，而服务端目前：

- `10502`（背包）**返回 0 件物品**；
- 没有称号数据；
- 因此这些"数字标签"拿不到值 ⇒ **停留在预建字形时的占位串 `+-0123456789`**。

**⇒ 这不是"下发了一个错误的字符串"，而是"这些字段我们没有下发任何值"。**

> ⚠ 我**没能**复现用户所说的"之前一次下发数值错误"。如果确实曾下发过该串，
> 它不来自当前代码/配置/数据库（三者都已逐字段搜过）。

## 五、用户已确认：问题界面 = **进图后的角色面板**

（不是登录页 —— 登录页实测正常。）

### 5.1 `form_pos_item` 是什么

`assets/src/game/form/form_pos_item.luac` 的字段与方法：

```
hero_head, career_icon, name_label, pos_num, take_lev, quality_bg,
setData, setFormPos, setPosStatus, requestPos, initView, initData
```

**⇒ 它是「阵型 / 上阵英雄位置」项**，`pos_num` 就是它的**位置编号数字标签**
（用 `ccui.TextAtlas:create('+-0123456789', …)` → 再 `setString(编号)`）。

### 5.2 它需要的数据来自哪条协议

`game/form/form_ctrl.luac` 的协议注册：

```
14000 14001 14002 14003 14004 14005 14006 14007 14008 14009 14099
13250 13251 13252 13253 13254
```

**⇒ 阵型数据属于 `14000` 系列。而实测 TCP 日志里，客户端
从未请求过任何 `1400x`/`1325x`** —— 说明阵型面板这条路还没走到。

### 5.3 装备位那几处呢

面板左侧的 武器 / 护手 / 鞋子 / 头盔 / 衣服 / 腰带 六个格子，每格后面一个
`+` 再跟 `+-0123456789`。这些格子里的数值来自**背包/装备数据**：

```
<< 10502 SCRoleBag bag_code=1, 0 items (9 bytes)     ← 我们回"0 件物品"
<< 10502 SCRoleBag bag_code=2, 0 items (9 bytes)
```

**⇒ 因为返回 0 件装备，格子的"数值标签"拿不到值 ⇒ 停在占位串。**
