## 二、★★ 一次"污染传播"的排查（本批最有价值的部分）

### 现象

回归里 `verify_arena.py` 突然 FAIL：
```
测试(2001) 看到的对手: [(1001, '测', 70, 1)]     ← 期望 'DSH'，实际 '测'
   !! 测试角色没把玩家看成对手
```

### 排查（三步）

1. **查 DB** ⇒ `roles.name = '测'`（**单字**，明显不是正常值）
2. **查谁改的** ⇒ 两个验收会改名字：`verify_10xxx_tail.py`（R166 新增）与 **`verify_unsupported4.py`**（R120 的 `10343` 验收）
3. **看 `verify_unsupported4` 的复原逻辑**：
   ```python
   name0 = db1('SELECT name FROM roles WHERE rid=?')   # ← 跑之前的名字
   …
   ask(10343, …str(name0)…)                            # ← 用 name0 复原
   ```
   ⇒ ★ **它用"当时的原名"复原** ⇒ 一旦 DB 被历史上某次**中断的测试**污染成 `'测'`，
   **它就忠实地把污染一直传播下去**（每次跑都维持 `'测'`）。

### 修（两处）

1. **`verify_unsupported4.py` 改用固定基准名 `DSH` 复原** —— 不再传播污染
2. **显式把 DB 恢复为 `DSH`**（新增 `tools/_restore_name.py`）

**修后**：
```
DB name: DSH
48 项回归失败数: 0      ← 全绿
```

> **★ 纪律第 21 条（R166）**：**验收"复原"时要用"固定基准值"，不能用"跑之前的值"** ——
> 否则**一次被污染的运行会把污染永久传播**，而且**看起来每次都是"正常复原"**。
> ★ 判据：**任何"记录原值 → 改 → 改回"的验收，都要问一句"原值本身可信吗"。**
