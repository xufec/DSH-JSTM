## 一、★ 症状与定位

重启后 `tools/verify_guaji.py`：

```
== 15403 合法怪 mon_bid=10101 ==
  code=1 ，但 kill_count: 20 → **20**（应 21）          ← 没累加
== 15403 未知怪 mon_bid=999999 ==
  code=1 msg=''（应 code=0 + '未知怪物(999999)'）      ← 没校验
```

**原因**：`if cmd == 15403` 有两处：

| 位置 | 内容 | 是否可达 |
|---|---|---|
| **L8663（靠前）** | 旧版：无条件 `code=1`，不累加计数 | ★ **命中** |
| L8694（靠后） | 新版：校验 `mon_bid`、`kill_count+1`、未知怪回 `code=0` | ❌ **死代码** |

⇒ 这正是本项目**第 8 次"分发顺序遮蔽"**，而这次是**专用分支遮蔽专用分支**。

## 三、修复 ②：给门禁补上"专用 vs 专用"检查（`duplicate_dedicated`）

`lint_dispatch_shadow.py` 原先只查「专用 ∩ 通用集合」——**对"同一命令两个专用分支"是盲区**。
新增 `duplicate_dedicated(src)` 并在 `main()` 里报告。

### ★ 这个检查我写错了两次，两次都靠自检发现（如实记录）

| 版本 | 做法 | 结果 |
|---|---|---|
| v1 | 直接扫原文 | **误报 38 条** —— 文件里大量**注释**引用了 `if cmd == N:` 片段 |
| v2 | 剥注释后，把 `if cmd == N:` 与 `if cmd in (…)` **混在一起**计数 | 仍误报 `20004/20016` —— 它们是**外层大元组里再嵌套子条件**（`if cmd in (20001..20017)` 内层又有 `if cmd in (20004,20016)`），**那是合法控制流** |
| **v3（采用）** | 只统计 **`if cmd == N:`** 这一种形式 | 真实文件**干净**；人为插入重复 `15403` ⇒ **被抓到**（自检 PASS） |

> **教训**：门禁自己也要有**自检**（构造一个"应该报错"的输入）。前两版如果只看"真实文件是否报错"，
> 会以为是"发现了 38 个 bug"而不是"门禁写错了"。
