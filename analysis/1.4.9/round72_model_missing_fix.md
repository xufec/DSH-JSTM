# R72：修复「到乾坤日月谷没有主角模型」+ 查清 `fight()` 的触发方式

> 用户报障：**之前到了乾坤日月谷有主角模型显示，现在没了**（我这几轮改动引入的回归）。
> 本轮定位到**两个叠加原因并都修掉**，另外顺手修掉一处**会说谎的日志**；
> 并查清了上一轮留下的"谁触发 `fight()`"。
> **时间**：2026-09-29 17:40 – 17:55。

## 一、★ 回归原因 A：切场景时**沿用了旧场景的坐标**

`_send_10200(bid)` 原实现**无论切到哪个图都用同一个存档坐标**：

```python
role = role_with_saved_pos(self.cfg)          # 永远是本地存档的坐标（属于 10001）
out = ... w_u16(role['x']) + w_u16(role['y']) # 切到 10005 时也照发 (91,56)
```

⇒ 客户端被告知"你在 **10005** 的 **(91,56)**"，而 (91,56) 是**史莱克城**的位置；
在乾坤日月谷里这个格子很可能在图外/不可走 ⇒ **摆不下主角 ⇒ 模型建不出来**。

**修**（`_send_10200`）：目标场景 ≠ 存档场景时，改用**目标地图的默认出生点**
（`Config.Map[bid].def_x/def_y`，同一份 `config_map.json`）：

```
.. 切场景 10001 -> 10005：坐标改用目标图默认点 (10,58)（原存档 (91,56) 是别的图的）
<< 10200 SCRoleEnter (server push) bid=10005 (10,58)
```

并记住这次的点（`self._last_enter`），供 `15402`（挂机怪坐标）复用 —— 否则两处各算一次坐标，
**怪会生成在别的图的坐标上**，玩家看不见怪。

## 二、★ 回归原因 B（更直接）：**重复推送了一次 `10201`，用的还是旧坐标**

`guaji_auto_start` 分支里，除了 `_send_10200()`（它内部**已经**推过 `10201`，且用的是修正过坐标的 role），
**又自己推了一次 `10201`**，而那一次的 role 是 `role_with_saved_pos()`（**旧场景坐标**）：

```python
self._send_10200(_map3)                       # 内部推 10201（role 坐标已修正）
_np5, _mn5 = scene_quest_extras(self.cfg, _map3)
self.request.sendall(pack_frame(              # ★ 又推一次 —— 用的是未修正的 role
    10201, build_10201([role_with_saved_pos(self.cfg)], _np5, _mn5, scene_elems(_map3))))
```

⇒ **第二次 `10201` 覆盖了第一次**，客户端最终按 (91,56) 摆主角 ⇒ 模型建不出来。
实测日志里 `10201` 连推两次、第二次是 (91,56)，而 `10200` 说 (10,58) —— 自相矛盾。

**修**：删掉这次重复推送（`_send_10200` 已经做了）。

### 修复后的实测序列（干净、自洽）


⇒ 主角确实被放在了**有效格子**上 ⇒ 模型应正常显示。

`10201` 共 3 次（对应 3 次 `10200`：登录 / 10300 补推 / 切挂机图），**不再有多余重复**。

## 三、顺手修掉一处**会说谎的日志**

原先这条 log 写在了 `if guaji_auto_start / else` 的**外面**：

```python
if self.cfg.get('guaji_auto_start'):
    ... 只排程、并未发送 ...
else:
    self.request.sendall(...15402...)
log('tcp.log', '  << 15402 进场景主动推 ...')   # ★ 两条路都会打这行
```

⇒ 走自动链时也会打一行"已推 `15402` (91,56)"，**而客户端根本没收到**。
实测证据：17:44:31 那条假日志之后，探针直到 17:44:47 才出现 `ghcreate`
（即**只有一次真推送**）。**已把该 log 移进 `else` 分支。**

> 教训：**日志是判据的载体，它自己说谎比没有日志更危险。**

## 四、★ 下一步已查清：`fight()` 由「**玩家点击场景里的怪**」触发

上一轮留下的"谁触发 `GhostMon:fight()`"：

```
ghost_ctrl proto#3（小回调，param=npc）：
    function(npc)  self:fight(npc.id, npc.bid)  end      ← 拿 npc 的 id/bid
ghost_ctrl proto#14（GhostCtrl:fight）：
    self.mon_hongchen:fight(a1, a2) …（各挂机线逐个转发）
ghost_mon proto#5（GhostMon:fight）：
    if self.mon_id then GetPrototype(15202); proto.mon_bid = self.mon_bid; SendProtocal() end
```

而 `ghost_ctrl proto#5 registerEvents` 绑的三个事件是
`SCENE_ADDMON` / **`SCENE_CLIENT_ELEM_CLICK`** / `SCENE_SUCCESS_GHOST`；
proto#3 的签名带 `npc.id/bid` ⇒ 对应 **`SCENE_CLIENT_ELEM_CLICK`**。

**⇒ `CS_15202` 不是自动发的，是"玩家点击地图里的挂机怪"才发。**
服务端对 `15202` 的应答（R69 已补）**已就位**。
