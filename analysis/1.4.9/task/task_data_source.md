# 任务数据来源（Phase 5A 审计）

> 问题：「任务配置来自 APK 本地资源、服务器，还是两者结合？」
> 结论：**C —— 本地配置（定义） + 服务器（状态）**（**已验证**）

---

## 一、结论

| 层 | 来源 | 内容 | 状态 |
|---|---|---|---|
| **任务"是什么"**（名字/描述/类型/等级/奖励/NPC/进度结构） | **APK 本地配置** | `assets/src/config/config_mission.luac` | **已验证** |
| **任务"什么状态"**（已接/进度/目标值/接取时间） | **服务器** | `SC_12400.mission_list`（13 字段） | **已验证**（结构）／**待验证**（完整闭环） |
| **任务的 UI/逻辑** | **APK 本地 Lua** | `game/mission/*`（含 68KB 的 `mission_util`） | **已确认** |

**⇒ 服务端**不需要**下发任务定义；它只需下发**任务状态**，
客户端自己按 `mission_bid` 去本地 `config_mission.luac` 取定义。**

---

## 二、本地任务配置（**已验证**）

文件：`assets/src/config/config_mission.luac`（约 504KB，18737 条指令）

| 指标 | 值 | 依据 |
|---|---|---|
| `Config.Mission` 条目总数 | **846** | 运行期全表扫描（Phase 4） |
| 其中 `progress` 非空 | **531** | 同上 |
| `progress` 赋值处 | **846 处**，且**全部能对回任务 bid** | 静态扫描 |
| 条目字段 | 36 个（`bid/name/desc/type/lev/progress/award_assets/accept_npc_id/commit_npc_id/…`） | 逐指令反汇编 |
| 任务 id 分段 | `100xx`（KSHORT）与 `350xx`（KNUM）等 | 反汇编 |

**样例（均为实测读出）**：

```lua
Config.Mission[10010] = { bid=10010, name='斗罗魂师',  desc='去周漪老师处报到', type=1 }
Config.Mission[10020] = { bid=10020, name='切磋魂技',  desc='与班长霍雨浩切磋', lev=2 }
Config.Mission[10070] = { bid=10070, name='巫风挑战',  desc='打败隔壁班的巫风', type=1 }
```

## 三、服务器侧应有的任务状态（**结构已确认**）

`SC_12400.mission_list` 的 13 字段（见 `task_data_model.md` §一）。

**⇒ 服务端只要为每条"玩家已接/可接的任务"填这 13 个值即可，
不需要下发名字、描述、奖励、NPC —— 那些客户端自己查本地配置。**

## 四、第一条任务的候选（**已确认存在于原版客户端**）

任务书要求：找一条**原版确实存在**、且**适合做第一条测试任务**的任务
（NPC → 接 → 简单条件 → 回 NPC → 奖励）。

**已从配置里实际读出的候选（都是真实条目，非编造）：**

| bid | 名字 | 描述 | type | progress | 备注 |
|---|---|---|---|---|---|
| **10010** | 斗罗魂师 | 去周漪老师处报到 | 1 (MIS_ZHU) | **空（0 条）** | 最简；但 `missionContent` 走分支④ 不动 |
| **10070** | 巫风挑战 | 打败隔壁班的巫风 | 1 (MIS_ZHU) | **1 条**（`prog[1]` 为 table） | 需要"击败"条件（战斗，本阶段禁止） |
| **10000** | （默认任务） | — | — | — | `MissionCode.defaultMissionId`，**非普通任务** |
| 35000 | 寻人 | 学院任务 | 6 (MIS_HUAN) | 1 条 | 循环任务族 |

**⇒ 结论：目前"读出来"的候选里，`10010`（去周漪老师处报到）**最接近**
"NPC → 接 → 回 NPC → 奖励"的最小闭环**（它是"去某 NPC 处报到"型）。

**⇒ 但"哪一条最适合"尚未定论** —— 还需要确认：
① `10010` 的 `accept_npc_id` / `commit_npc_id` 具体是谁；
② 它的完成条件（`progress` 为空，需搞清"空进度"如何被判定完成）；
③ 客户端对 `mission_status` 的具体取值期望。

**⇒ 这些留给 Phase 5E（单条任务数据结构）。本轮不选定、不实现。**
