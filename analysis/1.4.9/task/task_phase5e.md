## 一、结论先行：为什么选 `10010`

反汇编读出的 30 个字段里有两条**决定性**信息：

```
accept_npc_id = 0        ← 不需要 NPC 接取
auto_accept   = 1        ← ★ 自动接取
commit_npc_id = 10030    ← 去「周漪」（NPC 10030）提交
commit_talk   = 50010
```

**⇒ 这条任务的形态是：「进入游戏自动接取 → 去周漪处报到 → 提交领奖」**
—— 完全就是阶段 5 要的**最小闭环**，而且**省掉了"找 NPC 接任务"这一步**（`accept_npc_id=0`）。

**⇒ 这正好绕开了 5C 尚未打通的"点击 NPC 打开对话 UI"**，
是当前阶段**风险最低**的第一条测试任务。

## 三、任务从生到死的**完整数据流**（基于上面字段推出的形态）

```
① 角色登录 / 进场景
       ↓  auto_accept = 1、accept_npc_id = 0
② 服务端在 SC_12400.mission_list 里带上 bid=10010
   （或后续用 SC_12405 增量更新）
       ↓
③ 客户端按 bid 查本地 Config.Mission[10010]，得到：
     名字「斗罗魂师」/ 描述「去周漪老师处报到」/ 类型主线
     ★ 并在 NPC 10030（周漪）头顶画「可提交」标记
       ↓
④ 玩家去找 NPC 10030（周漪）
       ↓  commit_npc_id = 10030
⑤ 客户端发 CS_12403{mission_bid:10010}          ← 提交
       ↓
⑥ 服务端校验 → 回 SC_12403{mission_bid:10010, code:0, msg:''}
       ↓  并发奖（award_assets）+ 更新角色数据（经验/金币…）
⑦ 客户端刷新任务列表（SC_12401/12405）与角色数据（10301/10302/10303）
       ↓
⑧ 任务状态落库 → 退出重登后仍正确
```
