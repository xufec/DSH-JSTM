## 一、为什么能做这么多：这一族的**共性极强**

`105xx` 有 **40 条**未实现，我按规格一看，**几乎都是同一个模式**：

```
CS{bag_code:u8, eqm_item_id:u32, …}  →  SC{code:u8, msg:string, 回显…}
```

⇒ 与 R153 做的 `10529`/`10541` **完全同类**：**校验装备存在 + 如实 `code` + 回显参数**。

★ **这正是"从 1144 条里系统性升级"的高效路径**：**先看一族的共性，再批量处理**，
而不是逐条猜。

## 三、★ 又一次栽在 `string` 的长度前缀（纪律第 9 条）

`10590` 第一版 FAIL（回传列表读成 0 项、值是乱码）：

```
10590 回传列表 0 项 [131072, 720896] ⇒ ✗
```

根因：`SC{code:u8, msg:string, ItemIdList:table}` ⇒ `ItemIdList` 的计数在
**`1 + 2 + len(msg)`** 处，而我的 verifier 用了 `1` —— **漏了 string 的 2 字节长度前缀**。

⇒ 修（并写明布局）⇒ `10590 回传列表 2 项 [11, 22] ⇒ ✓`

> **这是本会话第 N 次栽在这一条**（R137 的 `15806`、R142 的 `20805`/`11606`/`11607`、
> 现在 `10590`）⇒ **纪律第 9 条要提升为"硬性检查"**：
> **凡解析含 `string` 的 SC，第一件事就是算 `2 + len`**。
