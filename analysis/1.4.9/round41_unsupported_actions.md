## 二、本轮真正的产出：26 条操作型 GAP 收口

### 2.1 问题

round39 把 65 条真实缺口按"SC 是否含结果码"分成两类：
- **39 条查询型** ⇒ 已用零值/空表诚实应答；
- **26 条操作型** ⇒ 当时判断"回成功是撒谎"⇒ **保持沉默**。

但沉默并不好：客户端**有处理器、在等应答**，面板会干等。
服务端对 `20001/20003/20004/20005/20016/20017` 早就确立了正确做法——
**"本阶段不实现，明确回失败"**。

### 2.2 做法

新增 `_UNSUPPORTED_ACTION_CMDS`（26 条）。应答 = **按 SC 规格**生成
`code/result = 0`（失败）+ `msg = '该功能暂未开放'`：

```
10206 00 0015 e8afa5e58a9fe883bde69a82e69caae5bc80e694be
      └code=0 └msg(len=21)"该功能暂未开放"
13402 0000 00 0000 00000000 00 0015 …    ← code 在第 5 位（id,type,buy_num,new_price,code,msg）
13020 0000 0015 …                          ← 首字段是 tips:u16
17301 00 0015 … 0000…                      ← 首字段是 result:u8，其后 14 个字段按规格补零
```

**三个诚实性要点：**

1. **回失败是真话**：这些玩法本服确实没实现 ⇒ `code=0` 如实反映。
2. **绝不回成功**：若回 `code=1`，客户端会以为（传送 / NPC 操作 / 商城购买 / 宗门战…）
   已生效，而服务端什么都没做 ⇒ 状态不一致，比沉默更糟。
3. **不是"编内容"**：`msg` 是服务端的**状态说明**（"未开放"），不是玩法数据。

### 2.3 实现方式

`_build_default_sc(cmd)` 扩展为 `_build_default_sc(cmd, code=1, msg=None)`：

- `code`：首字段名为 `code`/`result` 时写入的值（默认 1，保持既有 81 条行为不变）；
- `msg`：首个名为 `msg` 的 string 字段写入的文案（默认空串）。

⇒ 现有 81 条查询型**行为零变化**（回归验证见 §四）。

## 三、★ 顺带抓到的"审计工具"缺陷（当两个审计互相矛盾时，先怀疑检查器）

改造后出现一个耐人寻味的现象：

| 审计 | 结果 |
|---|---|
| `audit_sc_live.py --unsupported`（**在线**，按规格真解析） | **107/107 一致** ✅ |
| `audit_sc_conformance.py --generic --unsupported`（**静态**，算期望长度） | **26 条不一致** ❌ |

**在线审计与静态审计互相矛盾** —— 按"在线是真解析、静态是算长度"的分工，
问题必然出在静态侧的**期望模型**：它的 `default_len()` 仍假设
**所有 string 字段都是空串（2 字节）**，而新的"未开放"应答带了 21 字节文案。

修正 `default_len(fields, msg_len=0)` 后：**静态 106 一致 + 1 空规格 = 107**，与在线吻合。

> 教训：**审计工具本身要跟着产物演进**（round38 已踩过同源问题——
> 那次是"已展开的 items vs 字面引用"）。两个独立审计给出不同结论时，
> 是定位工具缺陷的最好信号。
