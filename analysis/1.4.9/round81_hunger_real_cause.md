## 一、★ 真源：`build_ctrl.luac` proto#2 的**默认值初始化**

```lua
self.stack_skill    = {}        -- 技能堆叠
self.stack_foods    = nil       -- 食物堆叠（初始为空）
self.hunger_val     = 65535     -- ★★ 饱食度**默认满值 = uint16 上限**
self.hunger_add_val = 0
self.hunger_need_coin = 0
```

而 `build_ctrl.luac` proto#0（`login_event_success` → `SCENE_START`）里：
`initData()` 之后**紧接着 `send13704()`** ⇒ 13704 是客户端登录后必发的第一条。

`hunger.luac` 里的行为：

| UI 元素 | 动作 |
|---|---|
| `coin_btn`「使用银魂币补充」 | **`send13771`** |
| 物品补充分支（`AssetsLessView`） | **`send13772`** |

| 文案 | `'剩余饱食度：'`、`'%s/%s'`（`hunger_val`/`hunger_max`） |

## 二、★★★ 「无法补充」的确切机制

**真机日志（用户点补充的那一刻）**：

```
[19:36:56] >> cmd=13771 ? body(4)=00 00 27 79
[19:36:56] << 13771 SC_13771 **默认响应** (12 bytes)     ← val = 0
[19:36:57] >> cmd=13772 ? body(4)=00 00 27 79
[19:36:57] << 13772 SC_13772 **默认响应** (11 bytes)     ← val = 0
[19:29:36] >> cmd=13704 → << 13704 **默认响应**
```

协议：

```
CS_13771（空） → SC_13771{val:uint16, price:uint32}          # 银魂币补充，val = **补充后的饱食度**
CS_13772（空） → SC_13772{code:uint8, msg:string, val:uint16} # 食用物品补充，val 同义
CS_13704（空） → SC_13704{lev1:u8 … lev4:u8}                  # 堆叠等级
```

**而 `13704/13771/13772` 全都躺在 `_GENERIC_DEFAULT_CMDS` 里** ⇒ 通用默认响应把
`val` 填成 **0** ⇒ 客户端把 `hunger_val` 从 **65535（满）写成 0**。

> **⇒ 每点一次"补充"，饱食度就被写成 0 —— 这正是"无法补充"，而且是"越补越空"。**

## 三、修复

新增专用分支（并**同时从通用默认集合移出**，否则会被遮蔽）：

| 命令 | 现在回什么 |
|---|---|
| `13704` | `SC_13704{0,0,0,0}`（结构照规格；**不编造等级**） |
| `13771` | `SC_13771{val=**65535**, price=0}` —— `val` 沿用客户端初始化的同一满值常量 `HUNGER_MAX`；`price=0` 是**未实现扣费**的如实标注，不编一个价格 |
| `13772` | `SC_13772{code=1, msg='', val=**65535**}` |

代码里加了常量 `HUNGER_MAX = 65535`，注释标明它来自 `build_ctrl.luac` proto#2。

## 五、★ 又一条方法学收获（这个 bug 家族的完整画像）

`13771/13772/13704/10640` **全都在 `_GENERIC_DEFAULT_CMDS` 里**，
它们的问题不是"没实现"，而是被"**回成功但全零**"的通用响应**假实现**了 ——
客户端拿到 `code=1` 以为成功，数值却是 0。

> **"安全默认响应"对"查询类"是安全的；对"带返回数值的动作类"则是危险的**
> —— 它会让客户端把 0 当真值。这类命令要么专用实现，要么放进 `_UNSUPPORTED`（回失败）。
> 排查入口：**凡是客户端点了没反应、或数值被清零的功能，先去 `_GENERIC_DEFAULT_CMDS` 里查它的命令号。**
