## 二、"去渠道登录"是怎么做的（复用既有工具，不新写）

`tools/patch_fake_login.py` 一步做三件**互相独立、各自断言**的事：

| # | 动作 | 效果 |
|---|---|---|
| **[1]** | DEX 单字节补丁：`Lcom/shiyue/sdk/EWanSdk;.<init>` 里 `const/4 v0,#0` → `#1` | `is_close = true`。EWanSdk **每个方法**都以 `if (!this.is_close)` 开头，且该字段全 dex 仅此一处写入 ⇒ **渠道 SDK 彻底静默**：不 init、不 login、不弹"初始化失败"框、不联网 |
| **[2]** | `assets/src/config.luac` 的 `URL_LUA_CONFIG` → `http://10.0.2.2:8080/...` | 启动配置指向**本地服务端**（绕过已停服的官方 CDN） |
| **[3]** | 向 `config.luac` 末尾追加 `server/dsh_fake_login.lua` 伪登录块 | Java 侧不再回调 `sdkBackInit/sdkBackLogin`，改由 Lua 自供 |

**"去渠道登录"与"适应现有服务端"其实是同一个补丁的两面**：[1] 去掉渠道依赖，[2]+[3] 接上我们的服务端。

## 三、★ 为多版本做的一处**必要重构**

`patch_fake_login.py` 原先把 CDN 地址**硬编码**：

```python
ORIG_URL = 'https://cdn.jstm.ewan.cn/update/config/url_config_ewan.lua'   # 只对 1.4.x 有效
```

1.3.0 用的是**另一个域名**：

```
URL_LUA_CONFIG="http://cdnres.jstm.shiyuegame.com/update/config/url_config_ewan.lua"
```

⇒ 首次运行 1.3.0 时 `[2]` 报 `expected exactly 1 URL_LUA_CONFIG, got 0` 并**中止**
（工具设计成失败即停，**不会产出半成品 APK** ✓）。

**改法**：把硬编码换成**按模式识别**（与 `tools/patch_dex_skip_sdkinit.py` 早已采用的
"按特征动态定位、不硬编码地址"同一思路）：

```python
m = re.search(r'URL_LUA_CONFIG\s*=\s*"([^"]+)"', cfg_old)
orig_url = m.group(1)                      # 各版本域名自动适配
```

> ★ 这正是"重构使之适应多版本"的核心：**把版本相关的常量从代码里拿掉**。
> DEX 那一步本来就是动态查 `field_ids` / `method_ids`，所以三个版本**偏移各不相同**
> （1.4.x `0x6DD549` / 1.3.0 `0x4DE101`）也能自动命中。

## 六、★ 实跑验证（MuMu，三个包都装上）

| 版本 | 包名 | 安装 | 实跑结果 |
|---|---|---|---|
| 1.4.9 | `...ewan.qihoo` | 原有 | 玩家正在玩（对照基线） |
| **1.4.11** | `...ewan.baidu2` | ✅ Success | ✅ **完全可用**：`10001 → 1110(account=dsh_local) → … → 10300 RoleInit`，**已进主城**，角色 DSH 可见，无渠道弹窗、无错误框 |
| **1.3.0** | `com.shiyue.dldl.ewan` | ✅ Success | ⚠ **能连、能登录，但重连循环**（见下） |

### 6.1 ★ 1.4.11：一次通过

```
>> cmd=10001 FirstPack
>> cmd=1110 CSAccountLogin body(187)  account=dsh_local     ← ★ 伪登录生效，无渠道阻塞
>> cmd=10302 / 13340 / 14901 / 10331 / 10303 / 15203 / 10999 / 12403
>> cmd=10103 RoleReLogin → 10921 → 10300 RoleInit → 10800 / 13300 …
```
截图确认：**主城、角色 DSH、可自由移动** ⇒「去渠道 + 接现有服务端」**端到端成立**。

### 6.2 ★ 1.3.0：补丁没问题，卡在**服务端缺命令**

现象：`1110 → 10102 → [15405/15400/15402/15403] 或 20002 → 断开 → 重连`，循环。

**关键观察**：1.3.0 的 `1110` body 只有 **22 字节**（1 对参数，仅 `account=dsh_local`），
而 1.4.x 是 **219 字节**（10 对）—— 说明伪登录对双方都生效，**问题是别的**。

**归因：服务端侧命令缺口，不是补丁问题。**
- `15403` 原先**无人应答**（无专用分支、也不在两个集合里）⇒ 已补（回 code=1）
- 补后仍循环，且这轮它只发到 `20002` 就断 ⇒ 说明还有别的应答缺口（`15404`/`15420~15422` 等）
- **1.3.0 在登录后立刻走"挂机链"**，而挂机玩法本体我们**尚未实现**（刷怪/结算/轮次）

⇒ 结论：**1.3.0 要真正可用，需要补挂机玩法本体**（这是一个功能项目，不是打包问题）。

### 6.3 三版协议对照（支撑上面的判断）

| 命令 | 服务端(源于 1.4.9) | 1.3.0 包内定义 | 一致？ |
|---|---|---|---|
| `15400` | `{code:C, msg:s}` | 同 | ✅ |
| `15401` | `{loop_num:C}` | 同 | ✅ |
| `15402` | `CS{mission_bid:I}` → `{mission_bid,map_bid,x,y}` | 同 | ✅ |
| `15403` | `CS{mon_bid:I}` → `{code,msg}` | 同 | ✅ |
| `15405` | `{loop_count:H}` | 同 | ✅ |

⇒ **协议层三版一致**，所以 1.3.0 的问题**确实在服务端未实现的功能**上，而不是版本不兼容。


补丁让客户端能**连上**我们的服务端；但**协议层是否完全兼容**取决于版本差异。
实测三版的核心协议定义：

| 版本 | `cmd_resolve` 段 | AutoConstruct 条目 | 核心命令规格 |
|---|---|---|---|
| 1.4.9 | 122 | 2463 | 基线 |
| **1.4.11** | 124 | **2542** | `10304/10306/13781/15402` **逐字一致** ✓ |
| **1.3.0** | 89 | **1600** | 同样**逐字一致** ✓ |

**结论**：
- **1.4.11 与 1.4.9 高度同族**（多 79 条命令，核心一致）⇒ 预期可直接对接；
- **1.3.0 是更早的版本**（命令集少 35%），核心命令规格仍一致 ⇒ 基本功能预期可用，
  但它**不会有** 1.4.x 才引入的玩法；
- 服务端只实现了"真机发过的子集"，所以**命令集大小差异通常不构成问题**。

**实跑验证已完成**（见 §六）：1.4.11 端到端通过；1.3.0 卡在服务端未实现的挂机玩法上。

## 七、★ 项目方反馈追踪："功能 UI 为空"（能进主城但主界面没按钮）

> 项目方反馈：**另外两个版本能进主城，但功能 UI 是空的**。以下是本轮的排查记录
> ——**两条假设已被证据排除**，一条被证实为登录所必需，真正的成因**尚未定位**。

### 8.1 ❌ 已排除：CDN 资源 404

初判：客户端启动会向我们拉 `url_config_ewan.lua`，再按 `%s/version2.txt` 比对版本、
按 `%s/assets` 取资源包；`server/cdn/` **目录根本不存在**，而 `/cdn/*` 的兜底是
**把 `version_text('208')` 当文件内容返回**（`mock_server.py` 内）⇒ 看起来必然 UI 缺失。

**但证据否掉了它**：`http.log` **92 万行里完全没有** `/cdn/`、`/assets`、`/update/`、
`version2` 的请求 ⇒ **客户端根本没走这条路**（1.4.9 的 `version_text=208` 恰好等于其本地版本，
不触发热更；另外两版虽本地版本不同，**实测也没发过这些请求**）。

### 8.2 ❌ 已排除：探针注入破坏了 UI（但证实**探针是登录必需**）

A/B 实验：把 1.4.11 用**轻补丁**重打（只改 URL + 只跳过 SDK 初始化，**不注入 Lua 探针**）：

```powershell
python tools/patch_url_only.py        anzbao/jstm_142165.apk patched/_t_urlonly.apk --base http://10.0.2.2:8080
python tools/patch_dex_skip_sdkinit.py patched/_t_urlonly.apk patched/_t_urlonly_sdk.apk
```

结果：安装启动后**卡在"正在加载"**，连主城都进不去。

⇒ 说明**探针是登录所必需的**（`is_close=true` 把渠道 SDK 整个静默后，
必须由探针的 Lua 提供 `sdkBackInit` / `sdkBackLogin`）。
⇒ 因此"去掉探针"不是解法；也**不能**据此断定为探针破坏 UI。

### 8.3 目前的实际状态

| 版本 | 登录 | 主城 | 功能 UI |
|---|---|---|---|
| 1.4.9（探针版） | ✅ | ✅ | ✅ 正常（对照基线） |
| **1.4.11**（探针版） | ✅ | ✅ | ❌ **空** |
| **1.3.0**（探针版） | ✅ | ⚠ 重连循环 | ❌ |

三个客户端**连的是同一个服务端**，用的是**同一份探针**；唯一差别是客户端版本自身。

### 8.4 ★ 下一步：把"哪条命令没被应答"按版本隔离出来

`tools/find_unanswered.py`（本轮新增）能列出"发了但没回"的命令，
但**当前日志混了三个客户端**。要定位就得**按版本隔离采集**：

1. 记录日志位置 → 只启动**一个**目标版本（`am force-stop` 其余两个）→ 等它进主城；
2. `python tools/find_unanswered.py --tail 3000` ⇒ 看它**独有**的未应答命令；
3. 与 1.4.9 的同项对比 ⇒ **1.4.11 多请求而 1.4.9 不请求、且我们没回的**，就是 UI 空白的候选；
4. 该命令补上应答后重测。

> 本轮 `find_unanswered` 已给出的**全局线索**（三版混合，仅作参考）：
> `10502`（背包查询）**100 发 / 22 应答**；`10001`（FirstPack）18 发 0 应答（**设计如此**，报到型无 SC）。

### 8.5 ★★ 隔离采集结果：**服务端应答是全的** ⇒ 成因在客户端侧

按 §8.4 的方法隔离，**只跑 1.4.11**（481 行窗口）后统计：

| cmd | 发出 | 应答 | 判断 |
|---|---|---|---|
| `10502` | 24 | 4 + 其余空表 | 1.4.11 一次请求 **12 个 bag_code**（`01 02 03 04 05 06 07 08 0c 0d 10 11`，各 2 次）；服务端按囊返回，**未实现的囊回空表**（不编造）——**不是漏答** |
| `10001` | 2 | 0 | **报到型，协议里无 SC** —— 1.4.9 同样不回（设计如此）|
| `10999` | 2 | 0 | 同上（CS-only）|
| `10300` | 1 | 0 | 同上（RoleInit 上报）|
| **其余全部** | ≥1 | **= 发出数** | **都有应答** |

⇒ **1.4.11 请求的每一条"需要应答"的命令，服务端都回答了。**
⇒ **"功能 UI 为空"不是服务端漏应答造成的。**

而客户端侧唯一被改动的东西就是**注入的 Lua 探针**（129KB，含 `install_login_hook` /
`installSceneViewHooks` / 定时 `step()` / `report()` 等大量 hook）。
它在 1.4.9 上正常，但 1.4.11 的模块结构不同，**很可能在 UI 初始化阶段抛错或改坏了某个类**。

### 8.6 ★ 实验结果：**探针不能靠"截断"瘦身**（A/B 不成立）

按 §8.5 的思路把实验做了：

```
最小探针 = dsh_fake_login.lua 的**前 176 行**（只留 URL 短路 + 伪 sdkBackInit/sdkBackLogin）
         = 6.3 KB（原 129 KB，缩小 20 倍）
语法门禁 node tools/lua-check/check.js ⇒ OK
打包 → 对齐 → 签名 → 安装 → 启动
```

**结果：❌ 卡在启动宣传画面**（"出版服务单位 / 审批文号"那一屏），
服务端日志里**从头到尾没有一条 `1110`** ⇒ 客户端**连账号登录都没发起**。

⇒ **探针里 178 行之后的部分不是"纯诊断"**，它与启动/登录链是**纠缠**的：
伪登录的 `step()` 要求 `sdkBackInit` 与 `ver_load_start` **同时**就绪，
而 `ver_load_start` 来自更新流程 —— 截断后这条时序断了。
⇒ **"无探针 A/B"用截断法做不到**；`功能 UI 为空`的成因**仍未隔离**。

**已恢复**：重装可登录的 `jstm_1411_fakelogin_aligned.apk`，确认能正常启动
（已走到过场动画 → 会进主城）；临时实验包已清理。

### 8.7 ★★ 实验二（版本开关）：**诊断块同样不能关** ⇒ 假设③ 也被否证

既然"截断"会断启动，改用**不删代码、只加开关**的办法（本轮已把开关加进探针）：

```lua
-- server/dsh_fake_login.lua 第 187 行起（诊断块）外面套一层
if not _G.__dsh_noprobe then
  ... 原有诊断/上报/hook 全部 ...
end
-- 默认不设标志 ⇒ 1.4.9 行为**完全不变**
```

产出 `server/dsh_fake_login_noprobe.lua`（置位标志 + 同一份内容），
打给 1.4.11。两份都过语法门禁。

**结果：❌ 依旧卡在版权/加载页（85 秒以上），服务端零 `1110`** ⇒ 连账号登录都没发起。

⇒ **关掉诊断 hook 也会打断启动** ⇒ **诊断块不是破坏 UI 的元凶**，反而是启动链的一部分
（很可能它的 tick 在驱动更新/登录时序）。

### 8.8 三条假设的最终状态：**全部被否证**

**现场**：已重装可登录的 `jstm_1411_fakelogin_aligned.apk`，确认**已进主城**

### 8.26 ★ 顺带修掉一个**真实的服务端 bug**（战斗结算线程反复抛异常）

读后台任务输出时，在 stderr 里发现成片的同一个异常：

```
Exception in thread Thread-XXXX:
  File "server/mock_server.py", line 5449, in _battle_settle
    drops = [(tb, item_name(tb), 1, ...
UnboundLocalError: local variable 'item_name' referenced before assignment
```

**根因（典型的"局部变量遮蔽模块级函数"）**：

```python
item_name(bid)                                    # 模块级函数（第 3521 行）

def _battle_settle(...):
    drops = [(tb, item_name(tb), 1, ...)]         # ← 这里调用它
    ...
    for item_bid, item_name, cnt, src in drops:   # ← 循环变量同名！
```

Python 只要函数体里**存在对 `item_name` 的赋值**（**循环目标也算**），
就把该名字在整个函数里视为**局部变量** ⇒ 上面的调用在赋值前执行 ⇒ 必崩。

**修法**：循环变量改名 `_iname`（不改语义，只消除遮蔽）。
修后脚本核查：`_battle_settle` 内**已无任何 `item_name` 赋值**；
重启后近期日志**不再出现该异常**。

> ★ 特征：**只在特定路径触发**（要有掉落且 `battle_test_drop` 打开），
> 又**抛在线程里** ⇒ 不会让主进程退出、只在 stderr 刷异常 ⇒ **容易被忽略**。
> **教训：后台任务的 stderr 要定期看。**
