## 一、★ 方法升级：把"缺口"变成可重跑的清单（`tools/gap_worklist.py`）

**问题**：`_GENERIC_DEFAULT_CMDS` 的"通用默认响应"保证了**结构正确、不卡死**，
但对**带返回数值的动作/查询类命令**，它会让客户端把 0 当真值
（R81 的饱食度、R86 的伙伴兑换都是这么坏的）。
可到底**还剩多少条、先修哪条**，此前没有依据。

**做法**：写了一个工具，从**真机真实日志**里配对 `>> cmd=N` 与 `<< N <描述>`，
统计"**只得到默认响应**"的命令，按真机热度排序，并交叉 `protocol/fields.json` 给出
"这条命令本该发什么"，再用 `--triage` 给出"可能的配置支撑"：

```bash
python tools/gap_worklist.py                 # 按热度列缺口
python tools/gap_worklist.py --triage --top 60 --md out.md
python tools/gap_worklist.py --cmd 14099     # 只看某条
```

★ **必须能只看最近日志**（`--tail`）：否则会把"已经修好的命令"（如 `16605`，R86 已实现）
的历史默认响应也算进来，清单就不反映**当前**缺口。

## 二、★★ 处置口径（三级，沿用方案 §P0-3 的统一验收）

| 级别 | 判据 | 处置 |
|---|---|---|
| **A. 做真实数据** | 能指到**原版配置表**或**本服 DB 表** | 按出处实现（如本轮 `14099`） |
| **B. 诚实空表** | 指不到数据源 | 保持"结构正确 + 空表"，**并登记理由**（进 `gap_triage`） |

> 会产生误匹配（例如 `18803` 匹配到 `_dial_reward.json` 并不合理）。
> **每条最终能不能做，必须人看配置内容后再定** —— 这是纪律，不是懒。

## 三、★ 本轮当场交付：清单第 25 条 **`14099`（阵型属性汇总）**

| 项 | 内容 |
|---|---|
| **真机热度** | 最近 2 万行被发 **16 次**，我们一直回默认空响应 |
| **规格** | `CS_14099`（空） → `SC_14099{attr_list:table(attr:uint8, value:uint32)}` |
