## 二、修掉的 6 个真实 bug

全部由本轮回放发现，且**根因都不是"实现得不够"，而是"编码与规格不符"**——
客户端要么读到错位数据，要么直接越界。

### 2.1 `10554` 背包移动：所有应答漏了尾部 `item_id`

- 规格 `SC_10554{code:u8, msg:string, from_code:u8, target_code:u8, item_id:u32}`
- 旧实现 6 处应答**全部**写成 `code + msg + frm + to`（28 字节，少 4）
- 真机 CS 佐证：`04 01 00000001 | 2d2d2d2d` = frm=4, to=1, item_id=1 + 4 字节残留
- **修正**：6 处统一补 `w_u32(item_id)`

### 2.2 `12832` 商城购买：字段宽度写错 + CS 读法错

- 规格 `SC_12832{code:u8, msg:string, id:u16, num:u16}` = 7 字节
- 旧实现：`struct.unpack_from('>I')` 读 id（把 id/num 拼成一个 u32），应答写 `u32(id)+u32(1)` = 11 字节
- 真机 CS 佐证（15 种样本同构）：`4e24 0001 | 138f0000` ⇒ **id=20004, num=1** + 4 字节残留
- **修正**：按 u16/u16 读，按 u16/u16 写

### 2.3 `13340` 个人名片：应答从 `gift_num` 起整段截断

- 规格尾部还有 `nice_num:u32, flower:u32, new_msg:u8, zone_skin:u16, head_skin:u16, use_badge_list:table`
- 旧实现到 `gift_num` 就结束 ⇒ 客户端解析越界
- **修正**：补齐 6 个字段（`use_badge_list` 发空表）

### 2.4 `10304` 角色属性大包：`attr` 被拍平成裸 u32 + 尾部 5 字段缺失 ★最严重

权威规格（`cmd_resolve_103.luac` AutoConstruct）：

```
attr__T__strength@H##intellect@H##armor@H##constiution@H
       ##atk_s@I##…##tenacity_rate_show@I
```

即 `attr` 是**表**：`u16 计数 + 1 条（前 4 项 u16 + 后 20 项 u32 = 88 字节）`。

- 旧实现（注释自称"字段顺序拉自 manual.md"）把 `attr` 当成 **24 个平铺 u32**（96 字节）写下，
  于是客户端把首 2 字节当表计数（读到 0）、**其后所有字段整体错位**；
  且 `mspd / animate_res / vip_exp / jiebai_title / jiebai_lev` **完全缺失**。
- **根因**：`manual.md` / `fields.json` 把这张表**拍平**成了顶层标量列表。
- **修正**：按权威规格写表 + 补齐尾部 5 个字段
- ⚠ 这是核心命令（真机 522 样本），值得单独记录

### 2.5 `16904` 在线时长：缺 `aim:u32`

- 规格 `{code:u8, msg:string, aim:u32}`；旧实现只写 `code+msg`（3 字节）⇒ 越界
- **修正**：补 `w_u32(0)`

### 2.6 `17602` 在线福利：`tips:u16` 被误写成 `code:u8`

- 规格 `{tips:u16, msg:string}`；旧实现写 `w_u8(1)+w_str('')`（3 字节）
  ⇒ 客户端把 `tips` 读成 `(1<<8|msg_len)`，随后 string 越界
- **修正**：改 `w_u16(0) + w_str('')`

## 三、剩余 5 条「规格不符」= **挖掘缺口**，不是服务端 bug

| 命令 | 未解析的嵌套引用 |
|---|---|
| `10401` 英雄背包 | `hero_bag.skill` |
| `10502` 角色背包 | `items.attrs_ext / attrs_ext_list / attrs_ext_one_list / jewel_list / str_ext_list` |
| `10800` 邮件 | `mail.assets / mail.items` |
| `10924` 活动列表 | `act_list.int_args` |
| `11215` 伙伴列表 | `partner_list.partner_attr / aptitude / skill / jindan_skill / talisman_skill / ext` |

**验证方式**：按 `D|Dsc10924int_args|` 当成 1 字节解析时，`消耗 = 74×4+2 = 298`
—— 正好等于审计报出的 298（真实应答 668）。⇒ 误判完全由"引用未解析"造成。

**根因（本轮新发现）**：`protocol/fields.json` 里虽有 472 个 `Dsc*` 条目，但它们

1. **字段顺序被反转** —— `Dsc19400attr_ext` 写成 `attr_str:u8, attr_ext_id:u32`，
   真实线序是 `attr_ext_id:u8, attr_str:u32`（`dsc_spec.py` 头注早已警告）；
2. 因此**类型也随之错位**（反转后首字段拿到下一字段的类型）；
3. 顶层规格里仍有约 **180 处** `D|Dsc*|` 保持**未展开**状态。

⇒ 需要一轮「**把 `D|Dsc*|` 引用展开为真正的嵌套 items，且以 reader 原型（不反转）为准**」，
才能让 fields.json 自洽、让自动校验不再有盲区。
