## ① 商城购买 `no such goods 20xx` —— ✅ **已修复并验证**

### 根因（日志实据）

`CS_12805{id:u16, num:u16}` 的 **`id` 是"商品条目主键"**，而不是物品 bid：

```
实测（tcp.log 原始请求体）：
   12805 body = 80 e9 00 01   → id=0x80e9=33001
   12805 body = 80 ea 27 0f   → id=0x80ea=33002
```

- **旧的手写商品表**用 `item_bid` 当主键 ⇒ 客户端发 `33001 / 33002`
- **新的原版商城表**（134 件）主键是 **`id`**（2001, 2002, …）⇒ 客户端发 **`20xx`** ← **正是用户看到的报错**

**原实现只按 `item_bid` 查 ⇒ 新列表下必然查不到 ⇒ `no such goods 20xx`。**

### 修复

**按 `id` 优先、回退 `item_bid`**（两种列表都能用）：

```python
g = None
for cand in src:
    if int(cand.get('id', -1)) == bid:   g = cand; break
if g is None:
    for cand in src:
        if int(cand.get('item_bid', -1)) == bid: g = cand; break
item_bid = int(g.get('item_bid', bid)) if g is not None else bid   # 入包用 item_bid
```

### 验证（独立 TCP 测试）

```
① 按商品 id=2001   : code=1  → gold −99   bag 25890: 3→4   ✓
② 按 item_bid=25890: code=1  → gold −99   bag 25890: 4→5   ✓
③ 不存在的 id=9999 : code=0 msg='no such goods 9999'        ✓
```

**⇒ 两条路径都通；非法 id 正确回 `code=0` + 非空 msg。**

## ② 任务可玩性 —— 第 1 步已完成：**「可接取列表」`12407/12408/12409`**

### 协议（`manual.md` 直读，**无 `D|Dsc*|` 未解子表**）

```
12407 (CS 空) → SC_12407 { add_mission_list : table(<13 字段，与 12400 同构>) }
12408 (CS 空) → SC_12408 { delete_list      : table(mission_bid:u32) }
12409 (CS 空) → SC_12409 { missions         : table(<13 字段>) }
```

### 设计依据（**为什么这样做**）

**剧情链是线性的** ⇒ 同一时刻**只能有一条**在"进行中"（否则任务栏同名重复）。
⇒ **链头**进 `12400`（已接取/进行中）；**链上后续**进 `12407/12409`（**可接取**，`status=0`）。
**⇒ 既能看到多条，又不会重名** —— 这正是这组协议存在的意义。

### 实现

```python
def accept_mission_rows(cfg, rid):
    """链头之后的、lev <= 玩家等级的 前 N 条（N = mission_accept_max，默认 6）"""
```

### 独立验证（直连 TCP）

```
SC_12400 (进行中):  [(10020, status=1)]
SC_12409 (可接取):  [(10030,0),(10040,0),(10051,0),(10052,0),(10053,0),(10054,0)]   ← 6 条
SC_12407 (add):     同上 6 条
SC_12408 (delete):  n=0
```

**⇒ 任务系统现在一次给出 **1 条进行中 + 6 条可接取 = 7 条可见**，且**进行中与可接取分开**、不重名。**

### 配置

```json
"mission_accept_max": 6
```

**⇒ 这解决了"任务栏只有 1 条、可玩性不高"的观感问题 —— 且**纯服务端、不碰客户端行为**。**
