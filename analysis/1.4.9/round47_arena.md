## 二、交付

### 2.1 新增存储（只有"服务端确实知道"的事实）

```sql
arena_state (rid PK, trophy, times, index_state, win_times, state, updated_at)
arena_record(rid, seq, type, opp_rid, opp_srv, opp_name, result, trophy,
             is_counterattack, reply_id, updated_at, PK(rid,seq))
```

列名**逐个对应协议字段**（不引入 `streak→state` 这类猜测映射）。

### 2.2 三条命令

| 命令 | 实现 |
|---|---|
| `11300` | `trophy/times/index_state` 取 `arena_state`；`pk_record` 取 `arena_record`（最近在前）；**`pk_show` 留空** |
| `11307` | `trophy` + 同一 `pk_record` 表体（共用 `arena_pk_record_body()`） |
| `11308` | `win_times` / `state` 取 `arena_state` |

**★ 为什么最初 `pk_show` 留空（严格不猜）**：

1. 本服是**单机**，没有其他玩家；
2. `config_arena_data` 只有 **3 条位置数组**（`22:[22,0,0]`、`10:[10…100]`、`140:[140…35]`），
   **不是对手表**；
3. 客户端 `trophy_arena_ctrl` 里**没有任何 proto 消费 `pk_show`**（已全文件搜过）。

⇒ 没有诚实来源，**不编造对手**。空列表是标准渲染路径，不会崩客户端。

### 2.3 ★ 对手源（项目方决策 A：本服已有角色互为对手）

留空是"没有来源"时的正确默认，但竞技场就此不可玩。项目方拍板采用
**决策 A**：对手 = **本服 `roles` 表里的其他角色**（R44 多角色能力的直接复用）。

```
SELECT rid,name,level,career,sex FROM roles WHERE rid<>? ORDER BY rid LIMIT 6
```

- 姓名/等级/职业/性别**全部取自真实角色行**；段位分取各自的 `arena_state.trophy`
  （没打过就是 0）—— **一个数值都不编造**；
- `id`（`CS_11302` 挑战用的槽位）按列表序 1..n 给出；
- `partner_list` 留空表（本服没有上阵伙伴数据来源，不编）；
- **不含自己**。

**实测**：

```
玩家(1001) 看到的对手: [(2001, 'R47测', lev=1, career=1)]
测试(2001) 看到的对手: [(1001, 'DSH',   lev=150, career=1)]
```

⇒ 单机下"要能打"就需要先有第二个角色；没有第二个角色时列表为空（仍是真话）。

## 三、★★ 第四次"分发顺序遮蔽" → 这次做了机械防护

R47 改完第一次自检就发现：

```
11300 in generic: True     ← 我的第一版编辑只加了注释、没删掉集合里的值
```

`13042` 已在 R46 修过，`11300/11308` 又差点重演。**这是同一坑的第四次**：

| 轮次 | 命令 | 后果 |
|---|---|---|
| round40 | `12901/12902/12911/12912/12931` | 5 个排行榜全返回全零 |
| round42 前后 | `13401/13403` | 商城真实商品列表被空表遮蔽 |
| R46 | `13042` | 爬塔面板永远没进度（真机 183 次） |
| R47 | `11300/11308` | 竞技场面板全零（真机 259/23 次） |

**规律：靠人工"记得移出集合"，总会漏。** ⇒ 新增 `tools/lint_dispatch_shadow.py`：

```
专用分支 161 条 ｜ 默认集合 65 条 ｜ 未开放集合 25 条
✓ 无分发遮蔽：所有专用实现都能真正执行。
```

做法：解析源码取出**专用分支命令集**与**两个集合的成员**，报告交集
（交集里的专用分支**永远不会执行** = 死代码）。已剥注释，避免注释里的数字被误收。

**灵敏度自检**（证明它真能抓到那四次那种错）：

```
假源: 专用=[11300,13042] 默认集合=[11300,13042]
遮蔽(默认): [11300, 13042]        ← 检出
✓ 注释里的 99999 未被误收
```

⇒ 建议把本 lint 加进"每轮收尾必跑"清单（与三道审计并列）。

## 六、★ 诚实结论：数据通路通了、对手也有了，但"战绩"仍**产不出来**

本轮把**存**、**读**、**对手源**都做通了，但**仍没有任何流程会写入 `arena_record`**。原因链：

```
要产生战绩 ⇒ 要打一场 ⇒ 要能挑战(11302) ⇒ 有对手 ✓（本轮已解决）
                                        ⇒ 但 11302 **真机一次没发过**，
                                          客户端发起挑战后的期望流程未取证
```

`SC_11302{code:C, msg:s}` 只是一个结果码 —— 胜负如何呈现给玩家
（是本地演算？还是等服务端推 `20020` 战斗结果？）**目前没有证据**。

⇒ 按决策 #4（严格不猜），**本轮不实现 `11302`**：给它编一套胜负结算规则，
等于把"占位数值"塞进玩家可见的战绩里。

**项目方已定向**：下一轮先做 **日常任务 / 成就**——
那是能**自然产生进度**的源头（而且不需要对手与战斗编排）。
`11302` 待玩家真正发起挑战、抓到实际流量后再实现。
