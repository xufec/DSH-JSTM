# 装备"被礼包占位、武器穿不上" —— 取证与修复

> 用户报障：「装备的武器被礼包占了位装备不了，其他 5 个装备成功」

---

## 一、★ 客户端取证：槽位由**服务端回包**决定

`backpack_ctrl.luac` → `handle_10511`（proto[34]，67 条字节码）：

```lua
handle_10511(self, resp, ...):
  @0  resp.code ...                              -- 先判成功码
  @3  BackPackConst.Bag_Code.BACKPACK ...
  @12 self.data
  @14 'rolePutOnEquip'
  @18 CALL                                       -- self.data:rolePutOnEquip(?, ?, ?)
  @19 resp.eqm_new_pos                           -- ★★ 槽位用的是**响应里的** eqm_new_pos
  @20 resp.bag_item_id
  @21 resp.hero_bid
```

**⇒ 结论（`CONFIRMED`）：`SC_10511.eqm_new_pos` 就是"穿到哪一格"。**

---

## 二、我的 bug（已修）

**原实现把 `eqm_new_pos` **硬编码为 0**：**

```python
pkt = pack_frame(10511, w_u8(1) + w_str('') + w_u8(0) +
                 w_u32(bag_item_id) + w_u32(eqm_item_id) + **w_u8(0)** + ...)
```

**⇒ 客户端拿到的槽位永远是 0 ⇒ 多件装备落到同一格 ⇒ 冲突/覆盖 ⇒ 用户看到"被占了位"。**

### 修复

```python
pkt = pack_frame(10511, w_u8(1) + w_str('') + w_u8(0) +
                 w_u32(bag_item_id) + w_u32(eqm_item_id) + w_u8(int(slot) & 0xff) + ...)
```

**实测：**
```
穿 bag_item_id=7 → SC_10511 code=1 **eqm_new_pos=1**   ← ✅ 返回真实槽位（不再是 0）
equip: [(1,7,33002), (2,17,41401), (3,18,41601), (4,19,41801), (5,20,41211), (6,21,41001)]
```

## 三、★ 但"哪件该穿哪一格"**仍缺证据**（如实）

### 我尝试了两条取证路线，都**没有**得到可靠答案

**路线 A：找客户端的装备部位常量**（`EquipPart` / `EquipType` / `ItemType` …）
**⇒ 全盘扫描：**一个都没找到**。**

**路线 B：从 `config_item.json` 用"物品 type"判定**
**⇒ 抽出来后**发现这个文件对装备类 bid 的抽取不可靠**：**

```
已成功装备的 5 件在 config_item.json 里：
   slot=3  bid=41601  name='2星转灵神丸'    ← 装备位里却被读成"神丸"
   slot=6  bid=41001  name='5'             ← name 是数字，明显错位
   其余多为 None
```

**⇒ 所以**不能**靠它判定"是不是装备"，更不能靠它定部位。**

**⇒ 因此我**没有**给 `equip_type_slot` 填任何映射 —— 它默认为空。**

## 四、我做了什么 / 没做什么（**边界清楚**）

| 项 | 状态 |
|---|---|
| **回包带上真实槽位**（`eqm_new_pos`） | ✅ **已修**（有客户端字节码依据，实测通过） |
| **按部位固定槽位**（武器→固定格） | ❌ **未做** —— **缺可靠的"物品部位"字段**，不臆断 |
| **拒绝非装备进装备槽** | ⚠️ 已留了机制（`equip_type_slot` 非空时会拒绝未命中的 type），**但因缺数据而未启用** |

**⇒ 所以我**没有**声称"武器被礼包占位"已彻底解决 ——
**我修掉的是可确证的那一半（回包槽位恒为 0）；另一半缺证据，如实留白。**
