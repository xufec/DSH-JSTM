## 〇、★ 优化总览（本轮，数据驱动）

### 用 cProfile 找到真正的瓶颈

```
一次 SC_12400 请求内部：
   mission_chain   被调用 2 次（重复）
   db_get_missions 被调用 4 次（重复）
   sqlite3.connect 被调用 **6 次**  ← 占该请求耗时的 **37%**
```

**⇒ 瓶颈不是"查询慢"，而是"**每次 DB 访问都新建+关闭连接**"。服务端是多线程
（`ThreadingHTTPServer` + `ThreadingTCPServer`）⇒ 用 **thread-local 连接复用**。**

### 实现

```python
_DB_LOCAL = threading.local()

def db_conn():
    """每线程复用一个连接；**每次交付都把 row_factory 复位**，防设置泄漏。"""
    con = getattr(_DB_LOCAL, 'con', None)
    if con is None:
        con = sqlite3.connect(DB_PATH, timeout=10); _DB_LOCAL.con = con
    con.row_factory = None
    return con

def db_release(con=None):
    """不关闭连接；只回滚未提交事务（异常中途退出不留脏事务）。"""
    ...
```

**替换 14 处 `sqlite3.connect(DB_PATH)` → `db_conn()`；14 处 `con.close()` → `db_release(con)`。**

## 三、★ 但发现一处**无谓 IO**（可优化，非瓶颈）

`mission_rows()` **每次调用**都做两件不必要的事：

1. **状态归一**（读全表 → 逐一比对 → 必要时写 DB）
2. **打日志**：`.. mission status normalized: chain_head=...`

实测：
```
mission_rows() x10 → 日志增长 610 字节（≈61 字节/次）
tcp.log 里已累计 78 行 "mission status normalized"
tcp.log 当前体积 567 KB
```

**⇒ 状态多数情况下**并没有变化**，却每次都写一行日志 ⇒ 长期运行会持续膨胀日志。**

### 建议（低风险，可选）

**把"归一"与日志改成"仅在状态真的发生变化时才做/才打"**：

```python
changed = False
for k, m in ...:
    ...
    if st != new_st:
        db_save_mission(...); m['mission_status'] = new_st; changed = True
if changed:
    log('tcp.log', '.. mission status normalized: chain_head=%s' % _head)
```

**⇒ 这不改变任何业务语义（状态仍会被归一），只是**去掉重复写库与重复日志**。**

### ★ 优化已实施（本轮）

**先取证后动手**：读代码确认 **`db_save_mission` 本来就是条件式的**（`if st != 2` 等），
**只有那行 `log()` 是无条件的** ⇒ 所以**只改日志**，风险最小。

```python
_changed = 0
...
    if st != 2:
        db_save_mission(...); m['mission_status'] = 2; _changed += 1
...
if _changed:
    log('tcp.log', '  .. mission status normalized: chain_head=%s (变更 %d 条)' % (_head, _changed))
```

### 验证

```

```

**语义未变（回归通过）**：
```

```

## 四、另一个重要发现（与速度无关，但一并记录）

| 观察 | 数据 |
|---|---|
| 客户端**确实请求过** `12407 / 12408 / 12409` | 历史日志各 **1 次**（本轮），服务端**都已正确应答** |
| 但用户实机看到任务列表**仍只有 1 条** | 「主线-切磋魂技」 |

**⇒ 我们**发了**可接取列表（6 条，`status=0`），但**客户端没有把它显示在任务列表里**。**

**⇒ 这意味着：`SC_12407/12409` 的 `mission_status=0`（可接取）可能**不是**任务栏列表的数据源**，
或客户端把"可接取"放在了**另一个 UI**（如 NPC 对话里的"可接任务"）。**

**⇒ 下一步若继续做 ②，必须先取证：包住客户端 `MissionCtrl` 上处理 `12407/12409` 的 handler，
看它把数据存到哪个容器、又被哪个 UI 读取 —— 而不是再猜一个 status 值。**
