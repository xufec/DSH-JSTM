## 二、★ 交付：三条命令

### 2.1 `13042` —— 爬塔进度面板（原先**全零**）

```
SC_13042{high_floor:I, ceng_list:T{ceng:C}, status:C, cur_ceng:C,
         left_time:I, clear_list:T{clear_ceng:C}, count:C}
```

| 字段 | 取值 | 依据 |
|---|---|---|
| `high_floor` | `dungeon_progress('tower_floor','21301')` | **与 `21301` 同一进度源**（口径一致） |
| `clear_list` | `dungeon_progress('tower_clear', *)` 的全部层 | 每通一层写一行 |
| `cur_ceng` | 同 `high_floor` | 与 21301 的 `floor` 保持一致 |
| `status` / `left_time` | 0 | 无原版依据 ⇒ 不编 |
| **`ceng_list`** | **空** | **可选层列表需塔配置支撑，其字段顺序未取证 ⇒ 按纪律留空** |
| `count` | `len(clear_list)` | 由已通关层推出 |

### 2.2 `13035` —— 层/轮次队伍信息（原先**完全无应答**）

```
SC_13035{team_list:T{ceng:C, index:C, round:C, time:C,
          member_list:T{rid:u32, srv_id:s, name:s, lev:u16, career:u16, sex:u8, guild_name:s}}}
```

单机形态：**一层一条、成员只有自己**。
成员字段**全部取真实角色数据**（rid/srv_id/name/lev/career/sex/gname，不是占位）；
`index/round/time` 无原版依据 ⇒ 留 0。⇒ 应答 27 字节，逐字段过规格。

### 2.3 `13038` —— 通关记录字符串（原先**完全无应答**）

```
SC_13038{record_str:string}    CS{Bid:u32, ceng:u8}
```

严格不猜：**没打过就是空串**（`w_str('')`，共 2 字节），
**不编造通关记录文本**。此条把"沉默"变成"明确的没有记录"。

> 客户端确有这三条处理器（`tower_ctrl`/`tower_view_new`/`demontower_view`），
> 所以此前是**真缺口**，不是"无害缺席"。

## 三、★★ 踩坑复现：**分发顺序遮蔽**（同一坑第二次）

改完第一次验证**失败**：

```
13042: high_floor=0 clear_list=[]       ← 我写的新实现没生效
21301: floor=7                           ← 同一角色，另一个命令是对的
```

**根因**：`13042` 仍在 `_GENERIC_DEFAULT_CMDS` 里，而**通用分支在文件里位置靠前**
⇒ 它先返回"规格正确但全零"的空表，我新写的专用分支**根本没执行**。

⇒ 把 `13042` 移出 `_GENERIC_DEFAULT_CMDS`，验证随即通过。

**这是本项目同一坑的第三次**（前有 `12931`/round40、`13401/13403`）。
`HANDOVER` §八 已把它写成纪律，本轮再次印证：

> **新增专用实现时，必须同时把该命令从 `_GENERIC_DEFAULT_CMDS` /
> `_UNSUPPORTED_ACTION_CMDS` 移出** —— 不移出，你的代码就是死代码。

**更值得记的是"它是怎么被发现的"**：不是靠肉眼审查，而是靠
**跨命令口径一致性断言**（`13042.high_floor` 必须等于 `21301.floor`）。
两个读同一份进度的命令给出不同答案 ⇒ 立刻暴露"有一个没生效"。
⇒ 这类**跨入口交叉断言**应继续写进验证脚本。
