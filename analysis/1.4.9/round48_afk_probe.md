## 五、A 路取证结果：找到了挂机配置，但仍**没有**"挂机线↔任务"的映射

### 5.1 `config_guaji.luac` = **挂机刷怪点配置**（已抽成 `server/_guaji.json`）

```
mon_bid    map_bid    lev_l  lev_r  disc
10101      10002      25     34     星斗大森林
10102      10007      35     44     明月森林
10103      10008      45     54     宁静海湾
10104      10004      55     64     明斗山脉
10105      10005      65     74     乾坤日月谷
10106      10009      75     84     魂殿遗迹一层
10107      10010      85     94     魂殿遗迹二层
10108      10011      95     104    魂殿遗迹三层
```

字段：`mon_bid`（刷的怪，对应 `config_mon`）/ `map_bid`（挂机地图）/ `disc`（地名）/ `lev_l~lev_r`（等级段）。
另有 6 条位置数组，是**地图分组**（如 `10002 → [10002,10007,10008,10004,10005,10009,10010,10011]`）。

★ **结论**：这张表是 **挂机地图↔怪**，**完全不含** mission bid 或日常 `huoli_id`
⇒ 「挂机线 ↔ 学院任务/监察任务」的对应关系**仍未被任何配置表达**。
（结合 §二.2：该对应关系在客户端是 `GhostMon` 实例，属于**运行时对象**。）

### 5.2 挂机为什么没启动？两条嫌疑，其中一条已被排除

| 嫌疑 | 证据 | 结论 |
|---|---|---|
| **① 地图缺失** | 服务端 `map_block.json` 支持 26 个场景，挂机图 `10002/10004/10005/10007/10008/10009` **都有**，但 **`10010`/`10011` 缺失** | **仍成立** |
| ~~② 等级越界~~ | 挂机点等级段只到 `lev_r=104`，玩家 150 级 | **已排除**：`automate_ctrl` proto#32 `GuajiMapList()` 只是「**当前场景 → 挂机条目**」的查表（`getCurSceneBid()`），**完全没有等级判断**；且客户端在 150 级下**确实**给出了「学院任务(今日已完成0/10环)」入口 |

### 5.3 ★ 客户端挂机入口的调用链（已定位）

```
automate_ctrl.luac   ← 读 Config.Guaji（挂机配置）
  proto#32 GuajiMapList() = GuajiMapList[getCurSceneBid()]      ← 场景 → 挂机点
  proto#30 / #41        = 用 getRoleVo() 做后续判断
```

**关键观察**：点「参与」之后客户端**只发 `10204`（移动）与一条 `15405`**，
**从未发 `10200`（进入角色/场景）** ⇒ 客户端**根本没尝试进入挂机场景**。

⇒ 结合嫌疑 ①：最可能是**目标挂机图服务端缺碰撞/场景数据**（`10010`/`10011`），
或 `15405` 之后缺少某条服务端应答，导致客户端停在"走到 NPC"这一步。

**下一步的判定性实验**（成本都很低）：

| # | 实验 | 判定 |
|---|---|---|
| **1（先做）** | 用 `/DSH_ADMIN/setlevel?lev=100` 把**玩家角色临时**设为 100 级 → 重走「日常/参与」→ 看是否出现 `10200` | 出现 ⇒ 与等级段相关；不出现 ⇒ 是场景/前置问题（回到 2） |
| 2 | 补 `10010`/`10011` 的碰撞数据（`extract_config_mapblock.py`）后重走 | 出现 `10200` ⇒ 是地图缺失 |
| 3 | 抓 `15405` 之后客户端在等什么（看它之后有没有重发 / 超时提示） | 定位缺失的应答 |

> ⚠ 实验 1 会**临时改动玩家等级**（admin 接口本就是"在线热改等级 + 立即推送"），
> 必须**记下原值并立刻还原**（玩家为 `lev=150`），且只在 `tcp.log` 显示客户端空闲时做。

### 5.4 ★★ 决定性结果：缺的地图**补不了** —— APK 里就没有那些碰撞段

`tools/extract_config_mapblock.py` 重跑结果：

```
分段数 = 26，对齐场景 = 26，跳过（无碰撞数据）= 90
有数据场景: 10001 10002 … 10009 10100 10200 … 31000        ← 26 个
10010 -> 缺      10011 -> 缺
```

⇒ `_config_map_block.luac` 里**只有 26 个场景的碰撞数据**，
`10010`（魂殿遗迹二层）/`10011`（魂殿遗迹三层）**根本没有段可对齐**
⇒ **不是"我们没提取"，而是"客户端配置里就没有"**。

**这条把"补数据"这条路封死了**，也顺带说明：
- 挂机图 `10002~10009`（lv 25–84）**我们都有** ⇒ 低等级挂机理论上可行；
- `10010/10011`（lv 85–104）**双方都没有碰撞** ⇒ 客户端自己也不该依赖它。

### 5.8 ★★ 真正的卡点：`15405` 回的 `loop_count = 0`

```
CS_15405（空）  →  SC_15405{loop_count: u16}
```

- 服务端**没有专用实现**，`15405` 落在 `_GENERIC_DEFAULT_CMDS`（第 1536 行）
  ⇒ 回的是通用零值 ⇒ **`loop_count = 0`**。
- 语义：**轮次计数** —— 客户端问"有多少轮"，得到 **0** ⇒ **没有轮次可跑，挂机就停住了**。

**这条完美解释了全部现象**：为什么等级 150 与 70 行为一样、为什么角色只是走到位就停、
为什么一条 `124xx` 都没有 —— **挂机从未拿到可执行的轮次**。

## 七、★★ 实施与实验：挂机链**已被推进两步**，并找到了映射所在的命令

### 7.1 实现 `15405`（挂机轮次）

- `15405` **移出** `_GENERIC_DEFAULT_CMDS`（否则又被遮蔽），改为 DB 驱动：
  `SC_15405{loop_count}` ← 新表 `guaji_state`（**默认 0 = 维持现状**）
- 新增 `/DSH_ADMIN/guaji?n=<轮次>` 作为实验旋钮
- 验证：`SC_15405 len=2 解析=2 PASS  loop_count=0` ✓

### 7.2 ★ 实验证明它就是卡点（`loop_count=10` 后客户端立刻前进）

```
>> cmd=15405
<< 15405 SC_15405 loop_count=10        ← 我们的实现生效
>> cmd=10204                            ← 继续寻路
>> cmd=15400 ? body(4)=00 47 00 3b      ← ★★ 此前**从未出现过**的新命令！
```

⇒ `loop_count=0` 时客户端到此为止；给出非 0 轮次后，它**立刻推进到 `15400`**。
**卡点判定成立。**

### 7.3 实现 `15400`（启动挂机），并**发现映射所在的命令**

原先 `15400` 在 `_UNSUPPORTED_ACTION_CMDS` 回 `code=0「该功能暂未开放」`
⇒ 挂机链**断在这里**。已移出并改为回**成功**（`code=1`）。

顺着 154xx 段一查，**整条链的规格全部出现**：

| 命令 | 方向 | 规格 | 作用 |
|---|---|---|---|
| `CS_15400` | 空 | `SC{code:u8, msg:s}` | **启动挂机** |
| `SC_15401` | — | `{loop_num:u8}` | 轮数配置 |
| **`CS_15402`** | `{mission_bid:u32}` | `SC{mission_bid:u32, map_bid:u32, x:u32, y:u32}` | ★★ **任务 → 地图/坐标** |

```
15405(轮次) → 15400(启动) → 15402{mission_bid} ← ★ 这个 bid 就是我们找的"挂机线↔任务"映射
```

⇒ **不需要再猜**：只要让客户端走到 `15402`，它发来的 `mission_bid`
**就是我们要的那一行 JSON 的答案**（服务端日志会直接记下）。

### 7.4 实验开关已**复位**（安全）

`loop_count` 已用 `/DSH_ADMIN/guaji?n=0` **复位回 0**。
原因：`15400` 现在回成功，客户端会继续往 `15402` 走，
而 `15402` 尚无实现 ⇒ 可能让玩家停在"半启动"状态。
**默认 0 时行为与本轮改动前完全一致**（15405 回 0、15400 回成功但客户端不继续）。

### 7.6 ★★ 顺带查出一起**运维事故**：两个服务端同时在监听 9000

排查"`15402` 静默无应答"时发现：

```
TCP 0.0.0.0:9000 LISTENING 18072   ← 18:48:43 启动（新代码，有 15402）
TCP 0.0.0.0:9000 LISTENING 41732   ← 18:31:06 启动（旧代码，没有 15402）
```

**Windows 上两个进程都能绑上同一端口** ⇒ 连接**随机**落到其中一个
⇒ 表现就是"**同一个请求时好时坏**"：我的 `15402` 落到了旧进程 ⇒ 无 handler、无应答。

**根因**：`job_kill`（harness 后台任务）**没有连带杀掉底下的 python 子进程**，
旧服务端一直活着占着端口。

**处置**：`Stop-Process 41732`，确认只剩 18072 ⇒ `15402` 立刻正常（`len=16 解析=16 PASS`）。

> ★ **新增运维纪律（应并入 HANDOVER §5.5）**：
> **重启服务端后必须核对"只有一个进程在监听 9000"**：
> ```powershell
> netstat -ano | Select-String ":9000.*LISTENING"     # 应只有一行
> Get-Process python | Select-Object Id,StartTime
> ```
> 否则会出现"改了半天没生效 / 时好时坏"这类极难定位的现象
> （本轮为此多花了数轮排查）。
