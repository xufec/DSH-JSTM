## 一、D2 背包渲染问题分析

### 1.1 问题物品清单

| bid | 名称 | type | type_name | 品质[6] | 最大堆叠[8] | 图标bid[17] |
|---:|---|---:|---|---:|---:|---:|
| 28514 | 小型宝石袋 | 6 | 礼包 | 4 | 999 | 30035 |
| 28560 | 抽奖券 | 7 | 材料 | 3 | 999 | 28560 |
| 28515 | 庆典夏日时装券 | 5 | 消耗品 | 5 | 999 | 28515 |
| 21403 | 牧夫 | 43 | 主动符文 | 5 | 1 | 21403 |

**症状**：服务端 10502 协议报背包有 4 件物品，但客户端 UI 显示 0/150（空背包）。

### 1.2 对比：可正常渲染的物品

| bid | 名称 | type | type_name | 品质[6] | 最大堆叠[8] | 图标bid[17] |
|---:|---|---:|---|---:|---:|---:|
| 10001 | 1星香嫩豆腐 | 31 | 烹饪 | 1 | 999 | 10000 |
| 20001 | 灵性（技能书） | 4 | 技能书 | 4 | 999 | 20001 |
| 40005 | 见习长枪 | 100 | 角色装备 | 2 | 1 | 40001 |
| 28030 | 幸运币 | 0 | (无名称) | 4 | 999 | 28030 |

### 1.3 差异分析

**共同特征（问题物品）：**
- 28514/28560/28515 均为**活动/限时道具**（宝石袋、抽奖券、时装兑换券）
- 21403 为**主动符文**（type=43），属于较后期系统内容
- 4 件物品的品质值分别为 3/3/5/5，品质跨度大

**与正常物品的关键差异：**

| 维度 | 问题物品 | 正常物品 | 判断 |
|---|---|---|---|
| type 类型 | 5/6/7/43 | 0/4/31/100 | type 名称表均有定义，非类型识别问题 |
| 图标 bid 映射 | 30035 / 28560 / 28515 / 21403 | 10000 / 20001 / 40001 / 28030 | 映射模式不一致但均存在 |
| 物品来源 | 活动奖励 / 后期系统 | 基础消耗品 / 装备 / 技能书 | **差异显著** |
| 客户端资源依赖 | 活动 UI 资源包 / 后期系统图标集 | 基础 UI 资源 | **最可能根因** |

### 1.4 最可能假设（INFERENCE）

**假设 1：客户端图标资源缺失（概率最高）**
- 客户端通过 item bid 查找图标资源（图标 atlas / sprite frame）
- 这 4 个 bid 对应的图标资源不在当前客户端资源包中
- 当客户端渲染背包 cell 时，找不到图标资源就跳过该 cell
- 4 件物品全部找不到图标 → 背包整体显示为空

**假设 2：客户端物品类型过滤**
- 客户端可能对 type=43（主动符文）、活动道具等有特殊渲染逻辑
- 当前客户端版本可能未加载这些类型的渲染模块
- 导致 cell 创建失败或被过滤

**假设 3：10502 协议数据格式不匹配**
- 服务端下发的物品字段格式与客户端预期不一致
- 客户端解析失败导致背包列表为空
- 但此假设与"4件特定物品"特征不符——格式问题会导致全部物品都失败

### 1.5 修复建议

| 优先级 | 方案 | 说明 |
|---|---|---|
| P0 | **服务端避免下发无图标物品** | 在 mock_server 背包同步逻辑中，过滤掉客户端无对应资源的物品 bid（type=43 符文、活动限时道具等），待客户端资源补全后再开放 |
| P1 | **补充图标资源映射** | 在客户端资源包中为这 4 个 bid 补全图标 sprite（需要从原版 APK 提取对应图标资源） |
| P2 | **验证 type 渲染逻辑** | 用已知可渲染的 type=5/6/7 物品（如商店售卖的消耗品）测试背包渲染，确认是否为类型问题还是具体 bid 问题 |
| P3 | **检查 10502 字段对齐** | 对比客户端协议解析代码，确认服务端下发的物品字段顺序/数量与客户端预期一致 |

## 二、掉落表结构盘点

### 2.1 配置位置

- **文件**：`server/cfg/config_drop.json`
- **主表**：`Drop`，共 **29 个掉落组**（按怪物 bid 索引，20001~20029）
- **关联**：每个掉落组通过 `mon_bid` 字段关联到对应怪物

### 2.2 掉落组字段结构

| 字段 | 类型 | 说明 | 示例 |
|---|---|---|---|
| mon_bid | int | 关联怪物 ID | 20001 |
| drop_type | int | 掉落类型标识 | 1 |
| coin | dict | 金币奖励范围 | {1000} |
| wood | dict | 木材/资源奖励 | {500} |
| normal | dict | **普通掉落物品池** | {4001: {1: {num, min, pp, max}}} |
| normal_sum | dict | 普通掉落概率汇总 | {hash: {"4001.0": 1000}} |
| core | int | 核心掉落物品 bid | 2001 (0=无) |
| core_p | dict | 核心掉落概率配置 | {1: {num:1, pp:1000}} |
| core_interval | int | 核心掉落间隔 | 0 |
| core_p_sum | int | 核心掉落概率总和 | 0 |
| first | int | 首杀掉落 bid | 0 (无) |
| first_p | dict | 首杀概率配置 | {} |
| holiday | int | 节日掉落 bid | 3001 |
| holiday_p | list | 节日概率配置 | [{1, 1000}] |
| holiday_key | int | 节日活动 key | 0 |
| over_type | int | 超额掉落类型 | 0 |
| morale | string | 士气/士气奖励 | (空) |

### 2.3 物品掉落条目格式（normal 子表）

```
normal: {
  "<item_bid>": {
    "<level>": {
      "num": <数量>,
      "min": <最小数量>,
      "max": <最大数量>,
      "pp": <概率点数 (probability points)>
    }
  }
}
```

**概率单位说明**：`pp` 字段值为 1000 时表示基础概率单位。具体概率 = pp / 该池 normal_sum 总和。

### 2.4 典型掉落组样例

| 怪物 bid | 金币 | 普通掉落 | 核心掉落 | 首杀掉落 |
|---:|---|---|---|---|
| 20001 | 1000 | 空 | 无 | 无 |
| 20003 | 1000 | 4001 (×1, pp=1000) | 无 | 无 |
| 20004 | 1000 | 4001 + 4003 (各×1) | 2001 (pp=1000) | 无 |
| 20005 | 2000 | 空 | 无 | 无 |

### 2.5 Phase 16 接线落点

| 内容 | 落点文件 | 落点字段 |
|---|---|---|
| 怪物掉落金币 | `server/cfg/config_drop.json` → `Drop.<mon_bid>.coin` | dict 格式 {min, max} |
| 怪物掉落物品池 | `server/cfg/config_drop.json` → `Drop.<mon_bid>.normal` | {item_bid: {level: {num, min, max, pp}}} |
| 核心/保底掉落 | `server/cfg/config_drop.json` → `Drop.<mon_bid>.core` + `core_p` | core=item_bid, core_p=概率配置 |
| 首杀奖励 | `server/cfg/config_drop.json` → `Drop.<mon_bid>.first` + `first_p` | first=item_bid |
| 节日/活动掉落 | `server/cfg/config_drop.json` → `Drop.<mon_bid>.holiday` + `holiday_p` | holiday=item_bid |

**注意**：当前掉落表仅 29 个组（覆盖怪物 20001~20029 基础怪），2645 只怪物中绝大多数没有独立掉落配置——它们可能共用基础掉落公式（金币按等级缩放 + 无物品掉落）。

## 三、UI 显示值核对

### 3.1 商城商品数量

| 数据 | 数量 | 来源 |
|---|---:|---|
| MallGoods（常规商城） | 110 | config_mall.json |
| MallXian（仙玉/元宝商城） | 45 | config_mall.json |
| MallWeek（每周限购） | 24 | config_mall.json |
| **配置总计** | **179** | — |
| 实机热卖页显示 | 8 | 运行时观察 |

**结论：INFERENCE — 分页/分栏目设计**
- 商城 UI 采用 Tab 分页（常规 / 仙玉 / 每周限购等）
- 热卖首页仅展示推荐 8 件商品，其余通过 Tab 切换浏览
- 179 是配置总量，不是单页显示量，差异合理

### 3.2 地图与 NPC 数量

| 数据 | 数量 | 来源 |
|---|---:|---|
| 配置总地图数 | 124 | config_map.json → Map |
| 配置总 NPC 数 | 456 | config_npc.json → Npc |
| MapNpc 表（地图-NPC 关联） | 54 条 | config_map_npc.json → MapNpc |
| 实机史莱克城 NPC 数 | 25 | 运行时观察 |
| 实机史莱克城怪物数 | 1 | 运行时观察 |

**结论：CONFIRMED — 场景局部加载模式**
- 124 张地图是全游戏总地图数，不是单场景同时加载的数量
- 456 个 NPC 分布在 124 张地图中，MapNpc 表（54条关联）定义了哪些 NPC 出现在哪些地图
- 实机单场景（史莱克城）只加载该地图配置的 NPC（25个）和怪物（1个）
- 这是典型的 MMO 场景局部加载设计——差异合理，非数据缺失
