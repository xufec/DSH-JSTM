## 〇、一句话结论

> ★ **找到并修正了点击路径的真正原因**：游戏窗口在 **Display #9**
> （`dumpsys activity activities` 里 `com.shiyue.dldl.ewan.qihoo/org.cocos2dx.lua.AppActivity` 的
> `mCurrentFocus` 落在 **Display #9** 下），而 `adb shell input tap` **默认打到 Display #0**
> ⇒ 我前几轮的点击**根本没到游戏**（这正是本项目文档里"游戏在非默认显示器上，screencap 抓不到"那条陷阱的同类）。
> 已改用 **`input -d 9 tap X Y`**（`input` 明确支持 `-d DISPLAY_ID`）。
>
> ★ **并用我自己的仪器证明了"输入现在确实送达"**：周期性 UI dump 在点击前后**发生了状态变化**
> （`节点=162 可点=53` → 点击后 `节点=140 可点=43` —— 即某个面板被打开/关闭）⇒ **UI 对输入有响应**。
> ⚠️ 但**仍未产生任何协议帧**（`12402/20002/15203/12400` 全 0）⇒ 我试的那几个节点**不触发服务端调用**，
> 需要更精确的目标（或改走探针直接调用客户端入口）。

## 一、本轮的关键修正（陷阱）

| 项 | 内容 |
|---|---|
| 现象 | 连续点击 7 次（含 `-d 9` 之前/之后），服务端**只看到 `1199` 心跳**，无任何任务/战斗帧 |
| 侦查 | `dumpsys activity activities`：`mCurrentFocus=Window{… com.shiyue.dldl.ewan.qihoo/org.cocos2dx.lua.AppActivity}` **归属 Display #9**；另有 Display #0 / #10（`mCurrentFocus=null`） |
| 根因 | `input tap` 不带 `-d` ⇒ 打到**默认显示器 #0**，游戏在 #9 ⇒ **点击丢失** |

| 旁证 | `dumpsys SurfaceFlinger --display-id` 显示物理 `mumuscreen008/009` 等 —— 逻辑 #9 与物理端口编号**不是一回事**（这也是本项目曾踩过的坑） |
