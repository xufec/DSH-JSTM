## 〇、一句话结论

> ① **触摸语义排除**：把"点一下"换成 **200ms 长按** 和 **显式 DOWN→150ms→UP**，两个精确坐标

> 那个问题在本环境下**仍是 UNKNOWN**。可依靠的事实仍只有一条：**服务端侧 0 字节**（多路验证过）。

### 2.1 为什么 v3 瞎、v2 不瞎（线索，留给下一轮）

- v2 挂了 120 个钩子（**每个模块各自的导出**），命中的是 `libandroid_runtime.so:sendto` /
  `libcutils.so:sendto` / `liblog.so:sendto` / `libc++.so:sendto` / `libc.so:sendto` …（**同一地址**）。
- v3 只挂 `libc.so` 的 5 个导出，却 0 命中 ⇒ 说明 `Module.findExportByName('libc.so','sendto')`
  在本环境解析到的地址**并不是**实际被调用的那个（ARM 翻译层 / 多套 libc 的典型症状）。
- ⇒ 下一轮应**回到 v2 的"全模块挂"策略**，再在上面叠加 `Socket.peerAddress(fd)` 过滤 :9000。

## 三、该怎么继续（下一轮直接照做）

1. **合并 v2 + v3**：用 v2 的"全模块逐导出挂钩"（已验证可信）＋ v3 的 `peerAddress(fd)` 过滤，
   得到可信的"发往 :9000 的次数/字节/失败数"。这一步做完，"帧到没到 socket 层"就有定论了。
2. 若结论是"从没写过 :9000" ⇒ 问题在**客户端 Lua→原生**这一段（与前面 SendProtocal/Encode 全 true 相符），
   应转向：让客户端**自己走完登录 UI**（需要一个能读图的模型来点界面），而不是继续探针驱动。
3. 若结论是"写了但 `sendto` 返回 -1" ⇒ 另一类根因（fd 未就绪/被断），可按 fd 状态继续查。
4. **不要再盲扫触摸**（本轮与第 3 轮合计 30+ 个坐标全部落空）；一律先 UI dump 拿坐标。
5. frida 纪律（已写入工具文件头）：**任何"0 事件"的结论，必须先用必然发生的写在同窗口自证**。
